## 一、请求源

- **流水线查表请求** `pl_search_req`
- **软件请求**：
  - `csr_req`：csr链读、写、search TCAM；
- **TCAM_ECC_FSM 请求**：
  - 写请求：ECC 1-bit 错误回写正确数据，优先级最高；
  - 读请求：巡检读 TCAM 数据用于 ECC 校验检查，优先级最低

> **说明**：搬移/清除请求**不是独立 ARB 请求源**——由软件寄存器配置触发、独立于 ARB 仲裁。其互斥性由硬件 `move_busy` 互锁 + 软件限制条款双重保障。

---

## 二、仲裁优先级

1. **TCAM_ECC_FSM 写请求**，优先级最高（搬移期间，巡检会被反压，因此不产生新写回）；
2. **流水线查表请求 vs 软件请求**：
   - 默认流水线查表请求优先级高于软件请求；
   - 内部实现计数器 + 配置寄存器，支持**机会式调度**与**饿死保护**；
3. **TCAM_ECC_FSM 读请求**（巡检），优先级最低。

---

## 三、move_busy 硬件互锁

搬移/清除不经过 ARB 仲裁，在ARB外层新增mux，哪个请求有效，访问使用哪个。二者本质上都是软件访问。为降低"可信软件假设"的依赖，增加硬件最终防线：

- 搬移 FSM 输出 **`move_busy`** 广播至 ARB；
- `move_busy` 有效期间，ARB **硬件强制 stall** 以下请求源的 grant：
  - **软件请求**（不依赖软件自觉遵守"搬移期间不下发命令"）；
  - **ECC 巡检读**（从源头阻断 ECC 写回触发链）；
- `move_busy` 期间**计数器暂停**，搬移完成恢复计数（避免"触发但无法 grant"的无效中间态）。

| 请求源 | 与 move 的协调机制 | 来源 |
|:---|:---|:---:|
| 流水线查表 | `pipeline_conflict`（搬移 FSM 自行避让流水线） | 已有 |
| 软件请求 | `move_busy` stall ARB grant（硬件互锁） | 本轮新增 |
| ECC 巡检读 | `move_busy` stall ARB grant（阻断写回触发链） | 本轮新增 |
| ECC 写回 | 由巡检读阻断天然规避，无需独立握手 | 本轮新增 |

---

## 四、计数器实现

| 项目     | 设计                                                                        |
| :----- | :------------------------------------------------------------------------ |
| 信号定义   | **`sw_waiting := sw_req_valid && !sw_grant && !move_busy`**（显式定义，消除实现二义性） |
| 加 1 条件 | `sw_waiting`                                                              |
| 清 0 条件 | 软件访问成功（`sw_grant`）；**行为 (b) 命令失效（`sw_discard`）后清 0 重新计数**                 |
| 暂停条件   | `move_busy`（搬移期间不计时）                                                      |
| 阈值触发   | `cnt >= csr_timeout_timer`（8bit 配置）                                       |
| 饱和行为   | 达到阈值后**不再 +1，保持原值**，直到软件访问成功或命令失效才清 0；**饱和计数，非回绕计数**                      |

## 五、行为触发（配置可选，互斥）

配置寄存器：

- `csr_timeout_timer`：8bit 超时阈值；
- `csr_timeout_pressure_pipeline_en`：
  - 1'b1，**行为 (a)**；
  - 1'b0，**行为 (b)**；

### 行为 (a)：反压流水线 1 拍

- 反压窗口：**固定 1 拍**（有界，非"直到软件完成"）；
- 反压 1 拍后等待下次流水线访问无效，软件 grant，软件访问完成（延迟不确定，与包源头到ARB路径延迟相关）；

> **v2.2 可行性闭环**：反压 1 拍后的等待时间在数学上无界，但工程实际不成立——架构时钟 930MHz vs 最高包率 905MHz，存在 **25MHz 系统余量**；且流水线天然存在空拍（包间隙 IFG、hash 冲突、后端反压），全满负载下软件仍可在空闲窗口内完成访问。**该关注点关闭，无需软件侧额外超时兜底** [^1]

### 行为 (b)：软件命令失效

- 通过 `sw_discard` **物理握手信号**通知源端命令已失效，源端撤销请求（**与 ARB 同时钟域，无需 CDC 处理**）；
- 命令失效后，认为此次命令已完成，计数器**清 0 重新计数**；

### 机会式调度（默认路径）

流水线天然存在空拍（包间隙、hash 冲突、后端反压），当 `pl_req == 0` 时直接 grant 软件，**零性能损失**。超时行为仅在流水线持续满负荷超过阈值时触发，反压频率趋近于零。

---

## 六、接口协议约束

- **保持协议**：源端 valid 在反压期间**禁止撤销**，必须保持到收到 grant（或 `sw_discard`）；
- **读操作接口占用 1 拍**，数据延迟走输出路径不影响反压窗口，固定 1 拍反压窗口充分；
- 无需 skid buffer——保持协议下在途请求不丢失，仅在源端等待；
- **`sw_discard` 与 ARB 同时钟域**，无需同步器，直接物理连线。

---

## 七、搬移 FSM 与 ECC 的接口协调

### 7.1 触发链阻断机制（取代 move_if_busy 握手）

ECC 写回不是独立异步请求源，其唯一触发链路为：

```
巡检读（源头）→ CE 检测 → 写回
```

设计验证结论：**搬移期间 ECC 巡检读不发起，则该链路在源头被阻断，写回请求不可能产生**。

实现基础：

1. `move_busy` 有效期间，ARB **不 grant ECC 巡检读**；
2. 巡检读被阻止发起 → 无新 CE 检测 → 无新写回 → **写回与搬移的接口竞争天然不存在**；
3. 因此**无需 `move_if_busy` 写回级握手**——互锁点已从"写回"前移至"巡检读"。

### 7.2 在途巡检读边界场景

巡检 FSM 若在搬移启动**前一拍**已发出读请求，数据返回与 CE 检测会落在搬移窗口内：

- 该巡检读合法，无需规避；
- 若检测出 CE，**写回请求以最高优先级直接抢占搬移接口**，搬移被反压；

> **v2.2 可行性闭环**：搬移 FSM 为**非原子性操作**，每个 T-cycle 都是独立完整的操作，周期之间的反压不破坏数据一致性。搬移 FSM 已有 `pipeline_conflict` 避让流水线的成熟机制，天然支持"被反压 → 保持当前状态 → 接口释放后恢复"的路径。ECC 写回抢占仅使搬移暂停在安全状态，待写回完成、接口释放后继续剩余步骤。**该关注点关闭，无需额外握手或暂存逻辑** [^1]

## 八、优先级全景图（两层仲裁机制）

| 优先级 | 请求源     | 仲裁层级              | 与搬移的协调                             |
| :-: | :------ | :---------------- | :--------------------------------- |
|  1  | ECC 写回  | ARB               | 搬移期间经巡检读阻断，不产生新写回；在途结果直接抢占搬移（搬移可接受反压） |
|  2  | 流水线查表   | ARB               | 搬移 FSM 通过 `pipeline_conflict` 自行避让 |
|  3  | 搬移操作    | 搬移 FSM 内部（不进 ARB） | —                                  |
|  4  | 软件请求    | ARB（带饿死计数器）       | `move_busy` 期间硬件 stall grant       |
|  5  | 清除操作    | 搬移 FSM 内部（不进 ARB） | —                                  |
|  6  | ECC 巡检读 | ARB（最低）           | `move_busy` 期间硬件 stall grant       |

**边界清晰**：ARB 只管流水线/软件/ECC 三类请求源；搬移 FSM 自行管理其 TCAM 接口占用，`move_busy` 广播提供硬件互锁，无需逐请求源独立握手。

> **v2.2 可行性闭环**：外层 mux 仲裁优先级语义（ECC 写回无条件抢占搬移）已在本全景图中显式化，RTL 实现直接遵循该优先级表即可，无需额外仲裁拍 [^1]

方案经多轮评审与可行性评估，**所有关注点已全部闭环**，可进入 RTL 实现阶段：

| 原关注点 | 关闭依据 | 状态 |
|:---|:---|:---:|
| 行为 (a) 反压后等待时间无界 | 全满负载下仍有系统余量（930MHz vs 905MHz，25MHz 余量），软件可访问 | ✅ 关闭 |
