## P/NP/CPL 报文
-  P，Posted 
	- **定义**：Posted事务无需目标设备的显式响应，发送后即视为完成。
	- **典型应用**：存储器写操作（Memory Write TLP）。
	- **特点**：低延迟，适用于对实时性要求高的场景（如数据传输），但无确认机制。
- NP，Non-Posted
	- **定义**：Non-Posted事务必须等待目标设备的响应（Completion报文）才能完成。
	- **典型应用**：存储器读请求（Memory Read）、I/O读写、配置读写等。
	- **特点**：确保数据可靠性，但会增加延迟，需通过响应验证操作结果。
-  CPL，Completion
	- **定义**：用于响应Non-Posted请求，携带数据或状态信息（如读数据、操作成功/失败）。
	- **细分类型**：
	    - **CPL**：不带数据的完成确认（如I/O写完成）。
	    - **CPLD**（Completion with Data）：携带请求数据的响应（如存储器读返回数据）。
	- **作用**：保证Non-Posted事务的原子性，确保请求方获取所需信息或确认。

### **总结与流程示例**

- **Posted事务**：CPU发送存储器写请求（P报文）→ 目标设备接收，无响应。
- **Non-Posted事务**：CPU发送读请求（NP报文）→ 目标设备处理→ 返回CPLD报文→ CPU接收数据。

## non-filt/filt 模式
### **1. Non-Flit模式（传统模式）**

- **定义**：  
    Non-Flit 模式是 PCIe 5.0 及之前版本的主要传输方式，其核心单元是**可变长度的事务层数据包（TLP）**。每个 TLP 的头部（Header）和有效载荷（Payload）长度不固定，需通过物理层的成帧标记（如 STP、END 等）界定数据包边界。
- **特点**：
    - **可变长度**：TLP 长度根据事务类型变化（例如读请求较小，写请求可能较大）。
    - **编码方式**：支持 8b/10b（Gen1-2）和 128b/130b（Gen3-5）编码，通过数据链路层数据包（DLLP）单独传输流控和确认信息。
    - **效率限制**：由于可变长度和额外的成帧开销（如 4 字节 PHY 层成帧标记），带宽利用率较低，尤其对小数据包不友好。
    - **错误处理**：依赖数据链路层的 CRC 校验和重试机制，但无前向纠错（FEC），需通过重传恢复错误。

---

### **2. Flit模式（PCIe 6.0引入）**

- **定义**：  
    Flit（Flow Control Unit）是 PCIe 6.0 的核心创新，采用**固定 256 字节长度**的数据单元，整合了 TLP、DLLP、CRC 和 FEC，成为链路层的基本传输单位。
- **特点**：
    - **固定长度**：每个 Flit 固定为 256 字节，包含 236 字节的 TLP 数据、6 字节的 DLLP 信息、8 字节的 CRC 和 6 字节的 FEC8。
    - **编码与速率**：强制使用 PAM-4 信号编码（4 电平脉冲幅度调制）以实现 64 GT/s 速率，并通过 FEC 增强抗噪声能力。
    - **高效传输**：
        - 消除 PHY 层成帧标记，减少冗余开销，带宽效率提升至 92%。
        - 支持多个 TLP 合并或拆分到一个 Flit 中，优化小数据包的传输效率。
    - **错误处理**：
        - 结合轻量级 FEC 和 CRC，可检测并纠正部分误码，减少重传概率，降低延迟。
        - 序列号（Sequence Number）和 ACK/NACK 机制支持批量确认，减少握手开销。
    - **低功耗支持**：新增 L0p 低功耗状态，允许动态调整链路宽度而不中断数据传输，仅限 Flit 模式。

---

### **3. 模式对比与适用场景** 

![[Pasted image 20250214094007.png]]

| **特性**    | **Non-Flit模式** | **Flit模式**      |
| --------- | -------------- | --------------- |
| **数据单元**  | 可变长度 TLP       | 固定 256 字节 Flit  |
| **编码**    | NRZ（Gen1-5）    | PAM-4（Gen6+）    |
| **带宽效率**  | 较低（成帧开销大）      | 高（无成帧标记，FEC 整合） |
| **延迟优化**  | 一般             | 显著降低（批量确认+小单元）  |
| **错误恢复**  | 依赖重传           | FEC+CRC+重传结合    |
| **协议版本**  | PCIe 1.0-5.0   | PCIe 6.0 强制启用   |
| **低功耗支持** | 仅 L0s          | 新增 L0p 动态调整链路宽度 |

---

### **4. 应用场景**

- **Non-Flit 模式**：适用于传统 PCIe 设备（如 Gen4/5 SSD、GPU），兼容性高，但性能受限。
- **Flit 模式**：专为 PCIe 6.0 设计，适合高吞吐、低延迟场景（如 AI 计算、数据中心互连），通过固定长度和 FEC 实现高效可靠传输。

---

### **总结**

Flit 模式通过固定数据单元和集成化设计，解决了传统 Non-Flit 模式在效率、延迟和错误恢复上的瓶颈，是 PCIe 6.0 实现 64 GT/s 速率的核心技术。未来随着 PCIe 6.0 普及，Flit 模式将成为高性能计算的关键支撑。

## PBR 报文
PBR 报文是指基于策略路由（Policy-Based Routing, PBR）的报文转发机制中，根据特定策略进行转发的数据包。PBR 是一种灵活的路由机制，允许网络设备不仅基于目的 IP 地址进行转发，还可以根据源 IP 地址、协议类型、端口号、VLAN ID 等多种条件来决定报文的转发路径458。

### PBR 报文的核心特点

1. **灵活的路由策略**
    - PBR 允许根据多种条件（如源/目的 IP 地址、协议类型、端口号、VLAN ID 等）定义转发规则，而不仅仅是依赖传统的路由表45。
    - 例如，可以将 HTTP 流量转发到特定链路，而将 FTP 流量转发到另一条链路，从而实现负载均衡或服务质量（QoS）优化5。
        
2. **优先级高于传统路由表**
    - 当设备配置了 PBR 后，匹配 PBR 规则的报文会优先按照策略进行转发，而不再依赖传统的路由表8。
        
3. **支持本地和接口 PBR**
    - **接口 PBR**：仅对从特定接口进入的转发报文生效，对本地生成的报文无效8。
    - **本地 PBR**：仅对设备本地生成的报文（如 ICMP 请求）生效，对转发的报文无效8。
        
4. **应用场景广泛**
    - 用于实现负载均衡、流量分流、服务质量（QoS）优化等58。
    - 例如，在多 ISP 连接的环境中，可以根据源 IP 地址将不同用户的流量分配到不同的 ISP 链路上5。
        

### PBR 报文的工作流程

1. **匹配规则**
    - 使用 ACL（访问控制列表）或其他条件（如报文长度、协议类型）匹配特定报文49。
2. **执行动作**
    - 根据匹配结果，将报文转发到指定的下一跳地址或接口49。
3. **优先级处理**
    - 如果报文匹配 PBR 规则，则优先按照策略转发；否则，按照传统路由表转发8。

# QA
## type0、type1 值得是什么呢？P2P 桥的信息嘛？
在 PCIe（Peripheral Component Interconnect Express）协议中，**Type 0** 和 **Type 1** 指的是 **配置空间头标（Configuration Space Header）** 的两种类型。它们用于区分 PCIe 设备的类型，具体如下：

---

### **1. Type 0 和 Type 1 的概述**

#### **（1）Type 0 配置空间头标**
- **设备类型**：用于表示一个 **端点设备（Endpoint Device）**。
- **特点**：
  - 端点设备是 PCIe 拓扑结构中的叶子节点，不能向下游扩展。
  - 通常用于实现具体的功能（如网卡、显卡、存储控制器等）。
- **配置空间**：
  - Type 0 配置空间头标包含设备的基本信息（如设备 ID、厂商 ID、类代码等）。
  - 不包含与桥接相关的字段（如下游总线号）。

#### **（2）Type 1 配置空间头标**
- **设备类型**：用于表示一个 **桥设备（Bridge Device）**。
- **特点**：
  - 桥设备用于连接 PCIe 层次结构中的不同层级（如根复合体到端点设备，或两个 PCIe 总线之间的连接）。
  - 桥设备可以是 **P2P 桥（Peer-to-Peer Bridge）** 或 **根端口（Root Port）**。
- **配置空间**：
  - Type 1 配置空间头标包含桥接相关的字段（如下游总线号、次级总线号、子级总线号等）。
  - 用于管理下游设备的配置空间访问。

---

### **2. Type 0 和 Type 1 的区别**

| 特性                | Type 0（端点设备）               | Type 1（桥设备）                 |
|---------------------|----------------------------------|----------------------------------|
| **设备类型**         | 端点设备（Endpoint）            | 桥设备（Bridge）                |
| **拓扑角色**         | 叶子节点，不扩展下游            | 中间节点，扩展下游              |
| **配置空间字段**     | 无桥接相关字段                  | 包含桥接相关字段                |
| **典型设备**         | 网卡、显卡、存储控制器等        | P2P 桥、根端口、交换机的端口等  |

---

### **3. Type 1 与 P2P 桥的关系**
- **P2P 桥（Peer-to-Peer Bridge）** 是一种特殊的桥设备，用于连接两个 PCIe 总线。
- P2P 桥的配置空间头标是 **Type 1**，因为它需要管理下游设备的配置空间访问。
- P2P 桥的主要功能是转发 TLP（事务层包）和管理下游设备。

---

### **4. 配置空间头标的字段示例**

#### **（1）Type 0 配置空间头标**
- **设备 ID（Device ID）**：设备的标识符。
- **厂商 ID（Vendor ID）**：设备制造商的标识符。
- **类代码（Class Code）**：设备的类型和功能。
- **BAR（Base Address Register）**：设备的资源分配（如内存或 I/O 空间）。

#### **（2）Type 1 配置空间头标**
- **下游总线号（Primary Bus Number）**：桥的上游总线号。
- **次级总线号（Secondary Bus Number）**：桥的下游总线号。
- **子级总线号（Subordinate Bus Number）**：桥下游的最远总线号。
- **BAR**：桥的资源分配（如内存或 I/O 空间）。

---

### **5. 配置空间的访问**
- PCIe 设备的配置空间通过 **配置事务（Configuration Transaction）** 访问。
- 配置事务的地址由 **总线号（Bus Number）**、**设备号（Device Number）** 和 **功能号（Function Number）** 组成。
- 配置事务可以是 **Type 0** 或 **Type 1**：
  - **Type 0 配置事务**：直接访问端点设备的配置空间。
  - **Type 1 配置事务**：通过桥设备转发到下游总线。

---

### **6. 总结**
- **Type 0** 和 **Type 1** 是 PCIe 配置空间头标的两种类型，分别用于端点设备和桥设备。
- **Type 0** 用于端点设备（如网卡、显卡），**Type 1** 用于桥设备（如 P2P 桥、根端口）。
- Type 1 配置空间头标包含桥接相关字段，用于管理下游设备的配置空间访问。
- P2P 桥是一种特殊的桥设备，其配置空间头标为 Type 1。

通过 Type 0 和 Type 1 的区分，PCIe 协议能够支持复杂的拓扑结构和设备管理。

## BAR
- BAR 的空间大小是由硬件决定的，并且在设备出厂时就已经固定。
- 硬件通过固定 BAR 的低位为 0 来指示设备支持的地址空间大小。
- 软件通过写入全 1 并读取 BAR 的值来确定这个大小。
- 这种方法确保了设备能够正确地向操作系统申请所需的资源。
## PCIe 中 Memory Write 操作是 Posted传输方式，若传输错误会引起什么后果以及如何补救呢？

在PCIe中，Memory Write操作采用Posted传输方式，意味着一旦请求发出，发送方不会等待接收方的确认。如果传输过程中发生错误，可能会引发以下后果：

1. **数据丢失或损坏**：由于没有确认机制，发送方无法得知数据是否成功写入目标内存，可能导致数据丢失或损坏。
    
2. **系统不稳定**：错误的数据可能引发系统崩溃、应用程序错误或其他异常行为。
    
3. **数据一致性问题**：如果部分数据写入成功而另一部分失败，可能导致数据不一致，影响系统功能。
    

### 补救措施

4. **错误检测与纠正**：
    
    - **ECRC（End-to-End CRC）**：PCIe支持ECRC，用于检测数据传输中的错误。若接收方检测到ECRC错误，可通过AER（Advanced Error Reporting）机制报告错误。
        
    - **AER（Advanced Error Reporting）**：PCIe设备可通过AER报告错误，系统软件可根据报告采取相应措施。
        
5. **重传机制**：
    
    - **Non-Posted传输**：对于关键数据，可采用Non-Posted传输方式（如Memory Read），发送方会等待接收方的确认，确保数据正确传输。
        
    - **软件重传**：在应用层实现重传机制，确保数据最终正确写入。
        
6. **硬件冗余**：
    
    - **冗余链路**：在高可靠性系统中，可使用冗余PCIe链路，确保一条链路故障时，另一条仍能正常工作。
        
    - **错误恢复机制**：部分高端PCIe设备具备硬件错误恢复功能，可自动纠正或重传错误数据。
        
7. **系统监控与维护**：
    
    - **定期监控**：通过系统日志和监控工具定期检查PCIe链路状态，及时发现并处理潜在问题。
        
    - **固件更新**：保持PCIe设备和系统固件的最新状态，修复已知错误并提升稳定性。
        

### 总结

PCIe的Memory Write操作采用Posted传输方式，错误可能导致数据丢失或系统不稳定。通过ECRC、AER、Non-Posted传输、软件重传、硬件冗余和系统监控等措施，可以有效检测和纠正错误，确保系统稳定性和数据完整性
## ID 路由时，EP 收到自身 function 下的包，怎么知道向哪个端口发出 CPL 包呢？

在PCIe系统中，当Endpoint (EP) 收到一个属于自身Function的TLP（Transaction Layer Packet）并需要发出一个Completion (CPL) 包时，EP需要确定将CPL包发送到哪个端口。这个过程主要依赖于PCIe的路由机制和EP的内部配置。以下是EP确定CPL包发送端口的具体步骤：

### 1. **TLP的路由信息**

- **Requester ID**：每个TLP都包含一个Requester ID，由Bus Number、Device Number和Function Number组成，标识了发起请求的设备。
    
- **EP的内部路由表**：EP内部通常有一个路由表，记录了不同Requester ID对应的端口信息。
    

### 2. **确定CPL包的发送端口**

- **查找路由表**：EP收到TLP后，会提取其中的Requester ID，并在内部路由表中查找对应的端口信息。
    
- **端口选择**：根据路由表中的信息，EP确定将CPL包发送到哪个端口。
    

### 3. **CPL包的构造与发送**

- **构造CPL包**：EP根据收到的TLP构造相应的CPL包，包含完成状态、数据（如果有）等信息。
    
- **发送CPL包**：EP将构造好的CPL包通过确定的端口发送出去。
    

### 4. **示例**

假设EP收到一个Memory Read请求TLP，Requester ID为Bus 1, Device 2, Function 0。EP会执行以下步骤：

- **提取Requester ID**：EP提取TLP中的Requester ID（Bus 1, Device 2, Function 0）。
    
- **查找路由表**：EP在内部路由表中查找Requester ID对应的端口信息，假设端口为Port 3。
    
- **构造CPL包**：EP根据Memory Read请求构造CPL包，包含读取的数据。
    
- **发送CPL包**：EP通过Port 3发送CPL包。
    

### 5. **路由表的维护**

- **初始化配置**：EP的路由表通常在系统初始化时由软件（如BIOS或操作系统）配置。
    
- **动态更新**：在某些系统中，路由表可以动态更新，以适应拓扑结构的变化。
    

### 总结

EP通过提取TLP中的Requester ID并在内部路由表中查找对应的端口信息，确定将CPL包发送到哪个端口。这个过程依赖于EP内部的路由机制和配置，确保CPL包能够正确返回到发起请求的设备。
