## 1. 读操作延迟不一致（Feature vs. Read Operation 章节）

**问题：** 手册第二章 "Feature" 部分描述读延迟为 **1 cycle**，但第 13 页 "Read Operation" 中描述读操作需 **2 cycles** 更新数据。请确认该 IP 的**实际读延迟**是 1 cycle 还是 2 cycles？若两者均正确，请说明适用的场景差异（例如是否取决于流水线配置或输出路径是否插入寄存器）。

## 2. Valid 位与 Data/Mask 阵列的分离原因及可靠性方案

**问题：** 手册中 Valid 位与 Data/Mask 阵列物理分离，且拥有独立使能引脚 `VBE` 和输入引脚 `VBI`。

1. **架构考量**：该设计是为了支持独立的批量复位（`RST`/`FLUSH`）、降低查表功耗（预过滤），还是为后续对 Valid 位做可靠性加固（如 DICE/TMR）？请明确主要设计意图。
2. **可靠性方案**：Valid 位本身是否有内置的可靠性保护？若发生 SEU 导致 Valid 位从 0 变为 1，将导致无效条目被误搜索。供应商是否推荐或支持对 Valid 位采用 DICE、TMR 等加固方案？若支持，请说明实现方式与集成建议。

## 3. Data/Mask 阵列 "11" 编码的处理

**问题：** 手册中 Data/Mask 编码的 Data=1, Mask=1 被标记为 **"Prohibited"（禁止状态）**。

1. 若软件误将某条目配置为 11，TCAM 在比较操作中的行为是什么？是否会导致**误匹配**、**输出不定态**，或**内部电路损坏**（如短路、过大电流）？
2. 硬件是否存在**保护机制**（如写入时自动检测并拒绝 11 状态），还是完全依赖软件保证不写入该编码？
3. 若不存在硬件保护，Verilog 仿真模型对该异常状态是否会输出 X 态或报错？

## 4. ECC 校验实现方案

**问题：** 我们的应用场景对存储数据可靠性要求较高，计划采用 **硬件检测 + 硬件自动纠错 + 回写** 方案——1bit 错误由硬件直接纠正并写回阵列，同时上报错误所在 bank 号供软件记录归档。

1. **IP 内建 ECC 及硬件纠错**：该 TCAM IP 是否**内置**完整的 ECC 编解码逻辑（包括校正子计算、错误位定位、自动纠正并写回阵列）？还是仅提供原始数据+校验位，需在外部封装纠错与回写逻辑？若支持硬件回写，纠错-回写流程需要多少个时钟周期，是否对正常读/写/搜索访问造成阻塞？
2. **外部封装方案**：若 IP 不支持内置 ECC 编解码逻辑（即 IP compiler 直接生成带 ECC 特性的实例），需要在 IP 外部自行封装 ECC wrapper，是否有推荐的参考实现？

## 5. 工作频点支持范围

**问题：** 目前项目频点已调整为 **930MHz**，同时需支持低频 **660MHz** 的工作模式。

1. 该 TCAM IP 是否支持 **930MHz** 的工作频率？是否有在该频点下完成 **tap-out** 的案例可供参考？
2. 低频 **660MHz** 是否也在支持的频率范围内？
3. 频点切换时，IP 的时序、功耗等参数有何注意事项？
