该方案借鉴DDR Patrol Scrubbing的思路，在TCAM中实现后台ECC巡检，整体方向正确。以下从数字电路设计角度进行深入分析并提出优化建议。

### 一、方案可行性分析

**设计思路合理：** TCAM的搜索操作是并行比较，不存在常规的"读取时进行ECC纠错"的数据通路，因此后台巡检是实现ECC保护的合理选择[^1]。

**核心矛盾明确：** 方案正确识别了关键问题——巡检写回时与搜索操作的冲突，这一点是方案能否落地的关键。

### 二、关键问题与优化建议

#### 1. 巡检写与搜索的冲突处理（核心难点）

方案推荐的**方案A（valid位屏蔽）** 思路对，但需要补充几个关键细节：

- **valid位的原子性保障**：valid清零与数据写入之间，搜索通路看到valid=0的那一瞬间，该条目的比较结果如何？如果TCAM在valid=0时仍然读取存储单元进行预充电，可能导致错误匹配。**建议**：在valid置0后，插入一个等待周期确保搜索流水线清空该条目的影子，再进行数据写入。
- **valid位的可靠性**：方案提到valid位用DICE或TMR加固，这是必要的。但还需要考虑：如果valid位本身发生单粒子翻转（SEU）从0变成1，会导致一个无效条目被误搜索。建议在巡检FSM中定期检查valid位的状态一致性。
- **部分写入风险**：如果TCAM的写操作不是原子性的（如写数据需要多个时钟周期），中间态可能触发错误的比较结果。[^2]建议在valid重新置1**之后**，再插入1个周期的空泡，确保后续搜索不会看到陈旧的数据残影。

> **优化建议**：**采用方案A+原子写**——如果TCAM支持burst write且确保写操作在单个维护周期内完成（即数据、mask、AD一次性写入），则valid屏蔽窗口可控制在2-3个时钟周期，对搜索性能影响极小。

#### 2. 巡检与CPU写的仲裁

方案中的地址冲突检查是必要的，但实现上需要注意：

- **比较器窗口**：CPU写可能在巡检读之后、写回之前的任一时间点发生。需要用一个寄存器锁存巡检读的地址，并在整个WRITE状态之前持续比较。建议使用**2-deep FIFO**记录待巡检写的地址（支持乱序场景），而不是单寄存器。
- **CPU写后的ECC状态**：方案假设CPU写的数据已经正确，但需要确认CPU写是否也经过ECC编码。如果CPU写路径上已有ECC编码，那么跳过巡检写是安全的；如果没有，则CPU写本身可能引入ECC错误，需要额外考虑。

> **优化建议**：**增加ECC写路径检查**——在地址比较器中，同时检查CPU写是否携带ECC校验。若CPU写触发了ECC自动编码，则跳过巡检写；若CPU写是"裸写"（无ECC），则巡检写回仍然有必要。

#### 3. 地址生成器与巡检范围

方案提到"可配置扫描区间"是正确的[^3]，建议进一步明确：

- **起始地址与终止地址**：建议用两个寄存器配置，而非固定0~N-1。这允许软件在动态更新部分条目时，临时缩小巡检范围。
- **步长可配置**：对于高可靠性场景，可以配置为连续遍历；对于低功耗场景，可以配置为"每巡检N个条目后跳过M个条目"，降低活动率。

#### 4. 速率与带宽控制

方案提到的"仅空闲时巡检"和"令牌桶"是可选的，但需要关注以下细节[^4]：

- **空闲检测的可靠性**：TCAM的搜索请求队列可能具有流水线深度。需要确保"队列为空"不是一个中间态（例如：请求刚被取走、但还在搜索流水线中）。建议使用**流水线清空信号（pipeline flush）** 而非简单的队列空信号。
- **可编程空闲计数器**：建议以"时钟周期"为粒度，而不是"搜索操作次数"，因为搜索操作的延迟可能随匹配长度变化。

### 三、设计验证重点补充

方案中列举的验证要点是合理的，建议再补充以下内容[^5]：

**ai**: ## 方案分析

你提出的方案将ECC功能拆分为**硬件检测上报** + **软件纠错**，这与此前讨论的硬件自动巡检纠错（Patrol Scrubbing）是不同的设计思路。以下从数字电路工程角度分析该方案的可行性、优缺点及适用场景。

### 一、方案核心要点

| 环节 | 实现方式 |
|:----|:---------|
| **错误检测** | 硬件在维护读路径上实时计算校正子（syndrome），发现错误时锁存地址并上报中断 |
| **地址上报** | 记录首次CE/UE的entry地址、syndrome和bank号，寄存器 `write-1-clear` |
| **数据纠正** | 软件读取错误地址对应的条目，修正数据位，通过写操作回写 |

### 二、方案优势

1. **硬件逻辑简化**：无需实现巡检FSM的WRITE状态和地址冲突仲裁逻辑，省去valid位原子屏蔽机制，芯片面积和验证工作量减少[^1]。
2. **灵活可控**：软件可根据错误等级决定处理策略（例如CE累积超过阈值再修复，或推迟到业务低峰期处理）。
3. **避免写冲突**：软纠错由CPU主动发起，可与搜索操作自然错开，不存在巡检写与搜索的冲突风险[^2]。

### 三、关键风险与工程考量

#### 风险1：纠错延迟窗口内可能无法容忍

根据TCAM的存储特性[^3]，单次错误的纠正流程如下：

```
错误发生 → 硬件检测并上报中断 → CPU响应中断 → 读取错误条目 → 软件修正数据 → 写回纠正
```

这一流程通常需要**数十微秒至毫秒级**，在此期间：
- 若该条目被搜索命中，将直接输出错误数据（CE场景可能仍可接受部分错误比特，UE场景则可能造成功能异常）

**对比**：硬件巡检方案在巡检周期内（通常毫秒级）即可完成纠错，若巡检频率足够高（如每100μs扫描一次），可大幅缩小错误窗口。

#### 风险2：不可纠正错误（UE）的发现时机

硬件巡检在扫描到UE时，可以在下一个读操作发生**之前**就锁定地址并触发中断。而软件驱动方案下，UE的发现取决于下一次**显式读操作**——如果该条目长期不被读取，错误将持续存在而无人知晓。

#### 风险3：多错误并发时的软件处理压力

若TCAM容量较大（如512×160），且在一定时间内多个条目同时出现CE，硬件仅上报首次错误地址，软件需要逐次处理，效率较低。建议硬件增加**错误缓存队列**（如4-deep FIFO），记录累计错误地址供软件批量处理[^1]。

### 四、两方案对比总结

| 对比维度 | 硬件自动巡检（原方案） | 硬件检测+软件纠错（本方案） |
|:---------|:---------------------|:--------------------------|
| **硬件复杂度** | 中等（需巡检FSM + 地址仲裁） | 低（仅错误检测 + 地址锁存） |
| **纠错延迟** | 微秒级（巡检周期内） | 毫秒级（依赖中断响应 + 软件处理） |
| **写冲突风险** | 需额外机制（valid屏蔽） | 无（软件写由CPU主动控制） |
| **UE发现速度** | 快（巡检到该条目时即发现） | 慢（取决于业务读访问频率） |
| **面积开销** | 较大（额外FSM + FIFO + 比较器） | 小（仅寄存器 + 中断逻辑） |
| **验证难度** | 高（需覆盖冲突、仲裁、边界场景） | 低（功能路径清晰） |

### 五、决策建议

- **优先选择硬件检测+软件纠错**，如果：
  - TCAM容量较小（如≤64 entries），巡检周期长、实时性要求不高
  - 芯片面积和验证资源紧张
  - 软件处理错误的中断响应延迟可接受（≤100μs级）

- **优先选择硬件自动巡检**，如果：
  - 可靠性要求极高（如电信设备、车规级）
  - 错误窗口不能容忍（条目错误后需立即修复）
  - TCAM容量大（如≥256 entries），巡检周期短

- **折中方案**：硬件负责**检测 + 对CE自动纠错**，对**UE仅上报地址**。这样既利用了硬件快速恢复CE的优势，又避免了UE场景下硬件误纠正的风险，是实践中较为均衡的取舍。

**ai**: # TCAM ECC 校验方案

## 1. 概述

本方案遵循 **硬件检测 + 软件纠错** 的设计思路。硬件负责后台巡检（Patrol Scrubbing）——定期遍历 TCAM 的 Data 阵列和 Mask 阵列，对每个条目进行 ECC 校验；当检测到可纠正错误（CE）或不可纠正错误（UE）时，锁存错误地址并上报中断，由软件读取错误条目并修正数据。

TCAM 采用 Data/Mask 独立双阵列架构 [^1]，每个阵列的每个 entry 作为独立的 ECC 保护域。

## 2. 硬件架构

### 2.1 巡检控制器 FSM

```
IDLE → READ → WAIT → CHECK → GAP → ADDR_INC → IDLE/READ
```

- **IDLE**：等待 `patrol_enable` 且定时器超时（定时周期可编程）。
- **READ**：通过维护接口发出读请求，读取当前地址的 entry（包括 Data+ECC 或 Mask+ECC）。
- **WAIT**：等待读数据及 ECC 校验结果（syndrome）。
- **CHECK**：
  - 无错误 → 直接进入 GAP。
  - CE/UE → 锁存错误地址（包括阵列选择、entry 号、syndrome 和位位置），触发中断，然后进入 GAP。
- **GAP**：插入可编程的空闲周期（节流控制），然后地址递增。
- **ADDR_INC**：更新地址，跳回 IDLE 或 READ。

### 2.2 地址生成与遍历顺序

地址生成器维护两个独立的地址计数器：`data_addr` 和 `mask_addr`，以及一个当前阵列选择标志 `sel_arr`。

- **遍历顺序**：先从 Data 阵列的 Entry 0 到 Entry N-1，然后切换到 Mask 阵列，从 Entry 0 到 Entry N-1，如此循环。
- **切换机制**：当 Data 阵列地址达到最大 entry 号后，`sel_arr` 翻转，地址计数器复位，开始遍历 Mask 阵列；Mask 遍历完成后，`sel_arr` 翻转回 Data，继续下一轮。
- **可配置参数**：
  - 起始/终止地址（支持子区间巡检）。
  - 步长（支持跳过配置，例如每巡检 N 条跳过 M 条）。

### 2.3 优先级与反压机制

ECC 巡检的优先级在所有访问源中**最低**，受以下约束 [^2]：

- 当软件通过维护接口读写 TCAM 时，巡检 READ 请求被**反压**（hold 或丢弃，取决于实现）。
- 当 TCAM 正在进行搜索操作时，巡检 READ 同样被反压。
- 巡检控制器在 IDLE 状态下持续检测维护接口的忙状态，仅当接口空闲时才启动 READ。
- 反压处理通过维护接口的 ready/valid 握手实现：巡检请求发出后，如果接口 busy，则暂停当前 FSM 直到接口释放。

### 2.4 ECC 编解码复用

ECC 编解码直接复用 TCAM 维护读路径上的现有 ECC 解码器（用于读校验）和维护写路径上的 ECC 编码器（用于写保护）[^3]。巡检读到的数据经过 ECC 解码得到 syndrome 和错误标志，但硬件不执行纠错写回，仅上报。

### 2.5 中断与错误记录

- **寄存器组**（每个阵列独立一组）：
  - `ERR_ADDR`：记录首次 CE/UE 的阵列（Data/Mask）和 entry 号。
  - `ERR_SYNDROME`：记录校正子。
  - `ERR_BIT_POS`：记录错误位位置。
  - `ERR_TYPE`：CE 或 UE。
- **中断触发**：边沿触发，检测到 CE 或 UE 时立即置位中断状态寄存器，软件读清。
- **累积记录**：若一个阵列在一次巡检周期内出现多个错误，硬件采用 **先到先锁** 策略（锁存首个错误地址，后续错误被覆盖，但可通过错误计数寄存器记录累计次数）。
- **CE 阈值告警**：滑动窗口内 CE 次数超过可编程阈值时，可额外触发一次告警中断，提示硬件可能劣化。

## 3. 软件纠错流程

1. 中断服务程序（ISR）读取 `ERR_TYPE` 寄存器，判断错误类型。
2. 根据 `ERR_ADDR`（含阵列选择）和目标 entry，通过维护接口读出完整的 entry 数据。
3. 软件根据 `ERR_SYNDROME` 和 `ERR_BIT_POS` 定位错误位，并修正（取反）。
4. 将修正后的数据通过维护接口写回原地址（注意写操作需遵循 TCAM 写时序，可能需分 Data/Mask 两次写入）。
5. 清除中断标志，恢复巡检。

> 注意：软件纠错期间，巡检仍可继续扫描后续地址，但若软件读取/写入的地址与巡检当前地址冲突，巡检会被反压，由硬件仲裁保证软件优先。

## 4. 节流与定时控制

- **定时启动**：`PATROL_TIMER` 寄存器配置巡检启动间隔（以时钟周期为单位），超时后巡检自动开始一轮扫描。
- **空闲间隙**：每个巡检 READ 之间插入 `GAP_CYCLES` 个空闲周期（可配置），确保巡检不占满维护接口。
- **反压计数**：可选的 `BACKPRESSURE_CNT` 寄存器记录被反压的次数，供软件评估巡检效率。

## 5. 关键设计考虑

## 1. 概述

本方案遵循 **硬件检测 + 软件纠错** 的设计思路。硬件负责后台巡检（Patrol Scrubbing）——定期遍历 TCAM 的 Data 阵列和 Mask 阵列，对每个条目进行 ECC 校验；当检测到可纠正错误（CE）或不可纠正错误（UE）时，锁存错误地址并上报中断，由软件读取错误条目并修正数据。

TCAM 采用 Data/Mask 独立双阵列架构 [^1]，每个阵列的每个 entry 作为独立的 ECC 保护域。Data 阵列与 Mask 阵列深度相同，一一对应 [^2]。

## 2. 硬件架构

### 2.1 巡检控制器 FSM

```
IDLE → READ → WAIT → CHECK → GAP → ADDR_INC → IDLE/READ
```

- **IDLE**：等待 `patrol_enable` 且定时器超时（定时周期可编程）。
- **READ**：通过维护接口发出读请求，读取当前阵列当前地址的 entry（包括 Data+ECC 或 Mask+ECC）。
- **WAIT**：等待读数据及 ECC 校验结果（syndrome）。
- **CHECK**：
  - 无错误 → 直接进入 GAP。
  - CE/UE → 锁存错误地址（包括阵列选择、entry 号、syndrome 和位位置），触发中断，然后进入 GAP。
- **GAP**：插入可编程的空闲周期（节流控制），然后地址递增。
- **ADDR_INC**：更新地址，跳回 IDLE 或 READ。

### 2.2 地址生成与遍历顺序

鉴于 Data 阵列和 Mask 阵列深度相同、一一对应 [^2]，地址生成器采用以下设计：

- **共用地址计数器**：维护一个 `entry_addr`（0 ~ N-1，N 为每个阵列的 entry 深度）。
- **阵列选择标志**：维护 1-bit `sel_arr`（0=Data，1=Mask）。
- **遍历顺序**：对于同一个 entry i，先读 Data[i] 校验，再读 Mask[i] 校验，然后 i 递增。具体为 Data[0] → Mask[0] → Data[1] → Mask[1] → …… → Data[N-1] → Mask[N-1] → 回到 Data[0] 开始下一轮。
- **地址更新机制**：每次 READ 完成后 `sel_arr` 翻转；当 `sel_arr` 从 1 回到 0 时，`entry_addr` 递增。
- **可配置参数**：
  - 起始/终止地址（支持子区间巡检）。
  - 步长（支持跳过配置，例如每巡检 N 条跳过 M 条）。

### 2.3 优先级与反压机制

ECC 巡检的优先级在所有访问源中**最低** [^3]，受以下约束：

- 当软件通过维护接口读写 TCAM 时，巡检 READ 请求被**反压**（hold，等待接口释放后重新发出）。
- 当 TCAM 正在进行搜索操作时，巡检 READ 同样被反压。
- 巡检控制器在 IDLE 状态下持续检测维护接口的忙状态，仅当接口空闲时才启动 READ。
- 反压处理通过维护接口的 ready/valid 握手实现：巡检请求发出后，如果接口 busy，则暂停当前 FSM 直到接口释放。

### 2.4 ECC 编解码复用

ECC 编解码直接复用 TCAM 维护读路径上的现有 ECC 解码器（用于读校验）和维护写路径上的 ECC 编码器（用于写保护）[^4]。巡检读到的数据经过 ECC 解码得到 syndrome 和错误标志，但硬件不执行纠错写回，仅上报。

### 2.5 中断与错误记录

- **寄存器组**（共用一组，通过阵列选择标志区分）：
  - `ERR_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_ENTRY_ADDR`：错误 entry 号。
  - `ERR_SYNDROME`：记录校正子。
  - `ERR_BIT_POS`：记录错误位位置（对于 CE）。
  - `ERR_TYPE`：CE 或 UE。
- **中断触发**：边沿触发，检测到 CE 或 UE 时立即置位中断状态寄存器，软件读清。
- **累积记录**：硬件采用 **先到先锁** 策略（锁存首个错误地址，后续错误被覆盖，但可通过错误计数寄存器记录累计次数）。
- **CE 阈值告警**：滑动窗口内 CE 次数超过可编程阈值时，可额外触发一次告警中断，提示硬件可能劣化。

2. 根据 `ERR_BANK`、`ERR_ARR_SEL` 和 `ERR_ENTRY_ADDR`，通过维护接口读出完整的 entry 数据。
3. 软件根据 `ERR_SYNDROME` 和 `ERR_BIT_POS` 定位错误位，并修正（取反）。
4. 将修正后的数据通过维护接口写回原地址（需遵循 TCAM 写时序，Data 和 Mask 需分别写入）[^5]。
5. 清除中断标志，恢复巡检。

### 3.2 UE（2-bit 错误）处理流程

1. 中断服务程序（ISR）收到 `int2`，读取 `ERR_TYPE` 寄存器确认 UE。
2. 根据 `ERR_BANK`、`ERR_ARR_SEL` 和 `ERR_ENTRY_ADDR` 定位错误位置。
3. 软件评估该条目的重要性，决定处理策略：
   - 若可重建 → 删除原条目，重新下发。
   - 若不可重建 → 标记该条目为无效，记录错误日志。
4. 清除中断标志，恢复巡检。

> **注意**：若同一个 entry 的 Data 和 Mask 均有错误，软件可在一次读操作中同时修正，分别写回 [^2]。

## 4. 节流与定时控制

- **定时启动**：`PATROL_TIMER` 寄存器配置巡检启动间隔（以时钟周期为单位），超时后巡检自动开始一轮扫描。
- **空闲间隙**：每个巡检 READ 之间插入 `GAP_CYCLES` 个空闲周期（可配置），确保巡检不占满维护接口。
- **反压计数**：可选的 `BACKPRESSURE_CNT` 寄存器记录被反压的次数，供软件评估巡检效率。

## 5. 关键设计考虑

### 5.1 Data/Mask 独立校验

由于 Data 和 Mask 是独立的 SRAM 阵列，分别具有独立的 ECC 校验位 [^1]，因此巡检必须分别遍历两个阵列。每个 entry 的 ECC 域仅包含该阵列的存储位，不跨阵列。

### 5.2 写冲突的避免

本方案采用**硬件检测 + 软件纠错**，硬件本身不执行写回，因此不存在巡检写与搜索的冲突问题 [^3]。软件纠错写入时，由 CPU 主动发起写操作，且 CPU 写优先级高于巡检读，软件可通过同步机制避免与搜索冲突。

### 5.3 错误窗口

从错误发生到软件完成纠错之间存在延迟（中断响应 + 软件处理），在此期间**该 entry 可能被搜索命中并输出错误数据**。对于 CE 场景，单比特错误可能仍可容忍；对于 UE 场景，软件响应时间必须控制在系统容错范围内。建议将 `int2`（UE）的中断优先级设置为最高，确保快速响应。

**ai**: # TCAM ECC 校验方案

## 1. 概述

本方案遵循 **硬件检测 + 软件纠错** 的设计思路。硬件负责后台巡检（Patrol Scrubbing）——定期遍历 TCAM 的 Data 阵列和 Mask 阵列，对每个条目进行 ECC 校验。当检测到错误时，根据错误类型上报不同等级的中断并锁存相关信息，由软件读取并修正数据。

TCAM 采用 Data/Mask 独立双阵列架构 [^1]，每个阵列的每个 entry 作为独立的 ECC 保护域。Data 阵列与 Mask 阵列深度相同，一一对应 [^2]。

### 中断分级

| 错误类型 | 中断等级 | 说明 |
|:--------:|:--------:|------|
| **1-bit 错误（CE）** | `int0`（普通中断） | 可纠正错误，软件可择机处理 |
| **2-bit 错误（UE）** | `int2`（致命中断） | 不可纠正错误，需软件立即响应处理 |

## 2. 硬件架构

### 2.1 巡检控制器 FSM

```
IDLE → READ → WAIT → CHECK → GAP → ADDR_INC → IDLE/READ
```

- **IDLE**：等待 `patrol_enable` 且定时器超时（定时周期可编程）。
- **READ**：通过维护接口发出读请求，读取当前阵列当前地址的 entry（包括 Data+ECC 或 Mask+ECC）。
- **WAIT**：等待读数据及 ECC 校验结果（syndrome）。
- **CHECK**：
  - 无错误 → 直接进入 GAP。
  - **CE（1-bit 错误）** → 锁存错误信息（Bank、阵列、entry 号、syndrome、错误位位置），触发 `int0`，进入 GAP。
  - **UE（2-bit 错误）** → 锁存错误信息（Bank、阵列、entry 号、syndrome），触发 `int2`，进入 GAP。
- **GAP**：插入可编程的空闲周期（节流控制），然后地址递增。
- **ADDR_INC**：更新地址，跳回 IDLE 或 READ。

### 2.2 地址生成与遍历顺序

鉴于 Data 阵列和 Mask 阵列深度相同、一一对应 [^2]，地址生成器采用以下设计：

- **共用地址计数器**：维护一个 `entry_addr`（0 ~ N-1，N 为每个阵列的 entry 深度）。
- **阵列选择标志**：维护 1-bit `sel_arr`（0=Data，1=Mask）。
- **遍历顺序**：先遍历 Data 阵列全部 entry（0 ~ N-1），再遍历 Mask 阵列全部 entry（0 ~ N-1），如此循环。具体为 Data[0] → Data[1] → …… → Data[N-1] → Mask[0] → Mask[1] → …… → Mask[N-1] → 回到 Data[0] 开始下一轮。
- **地址更新机制**：当 `entry_addr` 遍历完当前阵列的所有 entry 后，`sel_arr` 翻转，`entry_addr` 复位为 0。
- **可配置参数**：
  - 起始/终止地址（支持子区间巡检）。
  - 步长（支持跳过配置，例如每巡检 N 条跳过 M 条）。

### 2.3 优先级与反压机制

ECC 巡检的优先级在所有访问源中 **最低** [^3]，受以下约束：

- 当软件通过维护接口读写 TCAM 时，巡检 READ 请求被 **反压**（hold，等待接口释放后重新发出）。
- 当 TCAM 正在进行搜索操作时，巡检 READ 同样被反压。
- 当 TCAM 正在进行 valid reset、flush 等维护操作时，巡检 READ 被反压 [^5]。
- 巡检控制器在 IDLE 状态下持续检测维护接口的忙状态，仅当接口空闲时才启动 READ。
- 反压处理通过维护接口的 ready/valid 握手实现：巡检请求发出后，如果接口 busy，则暂停当前 FSM 直到接口释放。

### 2.4 ECC 编解码复用

ECC 编解码直接复用 TCAM 维护读路径上的现有 ECC 解码器（用于读校验）和维护写路径上的 ECC 编码器（用于写保护）[^4]。巡检读到的数据经过 ECC 解码得到 syndrome 和错误标志，但硬件不执行纠错写回，仅上报。

### 2.5 中断与错误记录

错误记录采用 **分类型独立寄存器** 设计：

- **CE（1-bit 错误）寄存器组**：
  - `ERR_CE_BANK`：错误所在 Bank 号。
  - `ERR_CE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_CE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_CE_SYNDROME`：校正子。
  - `ERR_CE_BIT_POS`：错误位位置（用于软件定位修正）。
  - `ERR_CE_COUNT`：CE 累计错误次数（软件读清，用于监测硬件劣化趋势）。

- **UE（2-bit 错误）寄存器组**：
  - `ERR_UE_BANK`：错误所在 Bank 号。
  - `ERR_UE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_UE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_UE_SYNDROME`：校正子。

- **中断触发**：
  - `int0`：CE 检测到后立即触发，软件读清。
  - `int2`：UE 检测到后立即触发，软件读清。

- **锁存策略**：硬件采用 **先到先锁** 策略（锁存首个错误信息，后续错误被覆盖）。

- **CE 阈值告警**（可选）：当 `ERR_CE_COUNT` 超过可编程阈值时，可额外触发一次告警中断，提示硬件可能劣化。

> **注**：2-bit 错误（UE）触发 `int2` 致命中断，要求软件立即处理，不存在"累积计数再触发告警"的需求 [^6]，因此 UE **不配备独立计数器**。CE 则可以通过计数器累积，用于监测硬件劣化趋势。

**ai**: ## 校正子（Syndrome）的定义

校正子（Syndrome）是 **ECC 解码过程中产生的中间计算结果**，而不是数据写入时生成的原始校验位。它与"校验位"是 ECC 流程中不同阶段的两个概念 [^1]。

### 写入 vs 读取 的区分

| 阶段 | 生成什么 | 做什么 | 存储位置 |
|:----:|:---------|:-------|:---------|
| **写入** | **校验位（Check Bits）** | 根据原始数据通过校验矩阵计算得到，与数据一起写入存储介质 | 存储在 SRAM 的 ECC 冗余位中 |
| **读取** | **校正子（Syndrome）** | 将读出的数据重新计算校验位，与原校验位异或比较得到 | **不存储**，实时计算，用于判断错误 |

### 校正子的本质

校正子是一个 **n 位的二进制向量**（n 为校验位数量），它的值直接指示 [^1]：

- **全 0**：数据无错误
- **非零且奇偶位匹配**：单比特错误（CE），校正子的值直接对应**出错比特的位置编号**
- **非零且奇偶位不匹配**：双比特错误（UE），说明错误不可纠正

### 以 (7,4) 汉明码为例

假设数据为 `1010`，写入时生成的校验位为 `101`（存储在冗余位）。

**读取时**：
1. 从 SRAM 读出数据 `1010` + 校验位 `101`
2. 硬件重新计算校验位 = `100`
3. 校正子 = 新校验位 XOR 原校验位 = `100 XOR 101` = `001`
4. **校正子 = 001（十进制 1）** → 表示第 1 位出错（如果出错位置是第 2 位，校正子就是 `010`）

### 在我们的方案中的应用

硬件巡检读出一个 entry 的数据后，ECC 解码器实时计算出 syndrome [^2]：

- CE 场景：syndrome 非零且指示具体错误位 → 硬件锁存 `ERR_CE_SYNDROME` 和 `ERR_CE_BIT_POS` 给软件
- UE 场景：syndrome 非零且无法纠错 → 硬件锁存 `ERR_UE_SYNDROME`，软件根据地址清除或重建该条目

### 总结

> **校正子 ≠ 校验数据**
> - 校验数据是在写入时计算并存储的
> - 校正子是在读取时实时比较计算出来的，不存储，仅用于判断错误类型和定位错误位置

- 汉明校验位 `P1=1, P2=0, P4=1`（偶校验）
- 全局奇偶位 `GP = 1`（使整个码字 1 的个数为偶数）

- 无错误：S = 0，GP 校验正确 → 判定**无错误**，数据直接输出。

### 二、CE 场景（1-bit 错误）

假设在存储过程中，**位置 5**（数据位 D2）发生单比特翻转：0 → 1。

读出码字变为：1 0 1 1 **1** 1 0 1（原位置5为0，现为1）。

硬件解码过程：

1. 重新计算汉明校验组：

   - 组1（位置1,3,5,7）：1 ⊕ 1 ⊕ 1 ⊕ 0 = 1（奇数）→ 应补 P1'=1

2. **硬件处理**：
   - 锁存 `ERR_CE_SYNDROME = 101`（表示位置5出错）[^2]
   - 锁存 `ERR_CE_BIT_POS = 5`（错误位位置）

### 三、UE 场景（2-bit 错误）

假设两个比特同时出错，例如**位置3（D1）和位置5（D2）**同时翻转：

- 原码字：1 0 1 1 0 1 0 1（含GP）
- 错误后：1 0 0 1 1 1 0 1（位置3从1→0，位置5从0→1）

硬件解码：

1. 计算汉明校正子：为1的位置编号异或。位置1,4,5,6为1 → 001 ⊕ 100 ⊕ 101 ⊕ 110 = (001⊕100=101, 101⊕101=000, 000⊕110=110)。校正子S=110（非零）。

2. 计算全局奇偶：原码字1个数为5（奇数），GP=1使总数为6（偶数）。错误后1个数为5（位置3少1，位置5多1，总体不变还是5？实际数：位置1,4,5,6共4个1，加上GP=1共5个，奇数）。GP校验=1（原始GP）是否正确？全局奇偶错误。

   **UE 判定**：全局奇偶正确 + 校正子非零 → 双比特错误（不可纠正）[^1]。

3. **硬件处理**：
   - 锁存 `ERR_UE_SYNDROME = 110`（但 UE 下 syndrome 仅用于记录，不用于定位单个位）[^2]
   - **不**锁存 `ERR_UE_BIT_POS`（UE 寄存器组无此字段）
   - 触发 `int2`（致命中断）[^3]
   - 软件收到中断后，读取 `ERR_UE_BANK`、`ERR_UE_ARR_SEL`、`ERR_UE_ENTRY_ADDR` 定位错误条目，根据策略（清除/重建/标记无效）处理。

这个问题值得仔细推敲。校正子（Syndrome）和错误位位置（Bit Position）之间存在信息冗余，但从硬件设计和软件接口角度，是否合并需要权衡。

### 一、两者的关系

以 (7,4) 汉明码为例：

| 场景 | 校正子（Syndrome） | 错误位位置（Bit_Pos） |
|:----:|:-----------------:|:-------------------:|
| **位置 3 出错** | `011`（二进制） | `3`（十进制） |
| **位置 5 出错** | `101`（二进制） | `5`（十进制） |

- Syndrome 是 **编码结果**，直接来自 ECC 解码器，值等于出错位置的二进制编码 [^1]
- Bit_Pos 是 **解码结果**，需要将 Syndrome 通过译码器转换成十进制位置编号

### 二、合并的可行性

**从信息量角度看，两者完全等价**：
- Syndrome 已知 → 可通过查表或组合逻辑得到 Bit_Pos
- Bit_Pos 已知 → 可通过逆向映射得到 Syndrome

**因此硬件上可以只存储 Syndrome，软件通过查表转换为 Bit_Pos。** 但这有前提条件。

### 三、合并的利弊

| 方案 | 硬件代价 | 软件代价 |
|:----|:--------|:--------|
| **存 Syndrome + Bit_Pos** | 多一个寄存器 + 译码器 | 软件直接使用，零转换开销 [^2] |
| **仅存 Syndrome** | 少一个寄存器 | 软件需实现 Syndrome→Bit_Pos 查表或计算 |

- **Syndrome 到 Bit_Pos 的映射表随 ECC 码字宽度变化**（8 位数据用 (12,8) 码、64 位数据用 (72,64) 码，映射表完全不同）[^1]
- 如果软件侧实现了通用查表，则可以统一处理；但若硬件直接提供 Bit_Pos，**软件无需关心 ECC 编码细节**

此外，Syndrome 对于 UE 场景仍有诊断价值（分析错误模式、判断故障与特定存储单元的关联），而 Bit_Pos 仅在 CE 场景有用 [^2]。若合并后仅保留 Syndrome，UE 场景不受影响，但 CE 场景软件需多做一步转换。

### 四、结论与建议

**技术上可以合并，但从工程角度建议保留两者**，原因如下：

1. **降低软件复杂度**：硬件直接提供 Bit_Pos，软件只需读取并取反即可修正，无需实现 ECC 解码表 [^2]
2. **隔离软件与 ECC 实现细节**：ECC 编码方案更改时，硬件更新译码器即可，软件接口不变
3. **验证简化**：软件处理路径更简单，减少软硬件协同验证的出错概率

如果你们项目中软件团队有能力实现通用 Syndrome 查表转换，且**硬件寄存器资源极为紧张**（例如每个 CE 寄存器组节省 32 位有意义），则可以合并。否则建议保持原设计。

### 二、FSM 设计建议

基于你的思路，推荐两种 FSM 实现方案：

#### 方案 A：拆分 READ 状态（推荐）

```
IDLE → READ_DATA → WAIT_DATA → CHECK_DATA → READ_MASK → WAIT_MASK → CHECK_MASK → GAP → ADDR_INC → IDLE/READ_DATA
```

- `READ_DATA`：通过维护接口发出 Data 阵列当前 entry 的读请求
- `WAIT_DATA`：等待 Data 阵列读数据及 ECC 校验结果
- `CHECK_DATA`：根据 Data 阵列校验结果锁存错误信息或直接跳转
- `READ_MASK`：通过维护接口发出 Mask 阵列当前 entry 的读请求
- `WAIT_MASK`：等待 Mask 阵列读数据及 ECC 校验结果
- `CHECK_MASK`：根据 Mask 阵列校验结果锁存错误信息或直接跳转
- `GAP`：插入可编程空闲周期
- `ADDR_INC`：递增 `entry_addr`，跳回 `READ_DATA`

**优势**：状态转移清晰，Data 和 Mask 的处理完全对称，便于 RTL 实现和验证。

#### 方案 B：复用 READ 状态 + 阵列选择标志

```
IDLE → READ → WAIT → CHECK → (sel_arr 翻转) → GAP → (sel_arr 从 Mask 回到 Data 时才 ADDR_INC) → IDLE/READ
```

- 保持原有 6 个状态不变，利用 `sel_arr` 区分当前读的是 Data 还是 Mask
- `CHECK` 阶段根据 `sel_arr` 分别写入 CE/UE 寄存器中的阵列选择字段
- `GAP` 结束后 `sel_arr` 翻转
- 当 `sel_arr` 从 1（Mask）回到 0（Data）时，`entry_addr` 递增

**优势**：状态数不变，与现有文档的 FSM 结构兼容，只需修改地址更新逻辑。

|:----|:-----------------|:-----------------|

| **清晰度** | 高，Data/Mask 处理路径明确 | 中，依赖 sel_arr 区分 |

| **推荐场景** | 新设计 | 在现有 FSM 基础上修改 |

### 四、地址更新逻辑（方案 B 示例）

```verilog
always @(posedge clk or posedge rst) begin
    if (rst) begin
        entry_addr <= 0;
        sel_arr    <= 0;  // 0=Data, 1=Mask
    end else if (state == GAP && gap_done) begin
        sel_arr <= ~sel_arr;           // 每次 GAP 后翻转阵列选择
        if (sel_arr == 1'b1) begin     // 当 Mask 检测完成
            entry_addr <= entry_addr + 1;  // 地址递增
        end
        // 若 Data 检测完成（sel_arr 从 0→1），仅翻转标志，地址不变
    end
end
```

### 五、遍历顺序对比

为便于理解，以 N=4 为例：

**原方案（逐阵列遍历）**：

```

```


**ai**: # TCAM ECC 校验方案

## 1. 概述

本方案遵循 **硬件检测 + 软件纠错** 的设计思路。硬件负责后台巡检（Patrol Scrubbing）——定期遍历 TCAM 的 Data 阵列和 Mask 阵列，对每个条目进行 ECC 校验。当检测到错误时，根据错误类型上报不同等级的中断并锁存相关信息，由软件读取并修正数据。

TCAM 采用 Data/Mask 独立双阵列架构 [^1]，每个阵列的每个 entry 作为独立的 ECC 保护域。Data 阵列与 Mask 阵列深度相同，一一对应 [^2]。

### 中断分级

| 错误类型 | 中断等级 | 说明 |
|:--------:|:--------:|------|
| **1-bit 错误（CE）** | `int0`（普通中断） | 可纠正错误，软件可择机处理 |
| **2-bit 错误（UE）** | `int2`（致命中断） | 不可纠正错误，需软件立即响应处理 |

## 2. 硬件架构

### 2.1 巡检控制器 FSM

```
IDLE → READ_DATA → WAIT_DATA → CHECK_DATA → READ_MASK → WAIT_MASK → CHECK_MASK → GAP → ADDR_INC → IDLE/READ_DATA
```

- **IDLE**：等待 `patrol_enable` 且定时器超时（定时周期可编程）。
- **READ_DATA**：通过维护接口发出读请求，读取 Data 阵列当前 entry 的数据（Data+ECC）。
- **WAIT_DATA**：等待 Data 阵列读数据及 ECC 校验结果（syndrome）。
- **CHECK_DATA**：
  - 无错误 → 直接进入 READ_MASK。
  - **CE（1-bit 错误）** → 锁存错误信息（Bank、Data 阵列、entry 号、syndrome、错误位位置），触发 `int0`，进入 READ_MASK。
  - **UE（2-bit 错误）** → 锁存错误信息（Bank、Data 阵列、entry 号、syndrome），触发 `int2`，进入 READ_MASK。
- **READ_MASK**：通过维护接口发出读请求，读取 Mask 阵列当前 entry 的数据（Mask+ECC）。
- **WAIT_MASK**：等待 Mask 阵列读数据及 ECC 校验结果。
- **CHECK_MASK**：
  - 无错误 → 直接进入 GAP。
  - **CE（1-bit 错误）** → 锁存错误信息（Bank、Mask 阵列、entry 号、syndrome、错误位位置），触发 `int0`，进入 GAP。
  - **UE（2-bit 错误）** → 锁存错误信息（Bank、Mask 阵列、entry 号、syndrome），触发 `int2`，进入 GAP。
- **GAP**：插入可编程的空闲周期（节流控制）。
- **ADDR_INC**：递增 `entry_addr`，跳回 IDLE 或 READ_DATA。

> **设计说明**：对于同一个 index，先完成 Data 阵列校验，再完成 Mask 阵列校验，然后才更新地址。这种设计确保同一个 entry 的 Data 和 Mask 错误在同一轮巡检中被连续发现，有利于软件一次性处理 [^2]。

### 2.2 地址生成与遍历顺序

鉴于 Data 阵列和 Mask 阵列深度相同、一一对应 [^2]，地址生成器采用以下设计：

- **共用地址计数器**：维护一个 `entry_addr`（0 ~ N-1，N 为每个阵列的 entry 深度）。
- **阵列选择标志**：维护 1-bit `sel_arr`（0=Data，1=Mask），由 FSM 状态隐式控制，无需独立寄存器。
- **遍历顺序**：Data[0] → Mask[0] → Data[1] → Mask[1] → …… → Data[N-1] → Mask[N-1] → 回到 Data[0] 开始下一轮。
- **地址更新机制**：当前 entry 的 Data 和 Mask 均校验完成后（即 CHECK_MASK 状态结束后），`entry_addr` 递增。
- **可配置参数**：
  - 起始/终止地址（支持子区间巡检）。
  - 步长（支持跳过配置，例如每巡检 N 条跳过 M 条）。

### 2.3 优先级与反压机制

ECC 巡检的优先级在所有访问源中 **最低** [^3]，受以下约束：

- 当软件通过维护接口读写 TCAM 时，巡检 READ 请求被 **反压**（hold，等待接口释放后重新发出）。
- 当 TCAM 正在进行搜索操作时，巡检 READ 同样被反压。
- 当 TCAM 正在进行 valid reset、flush 等维护操作时，巡检 READ 被反压 [^5]。
- 巡检控制器在 IDLE 状态下持续检测维护接口的忙状态，仅当接口空闲时才启动 READ。
- 反压处理通过维护接口的 ready/valid 握手实现：巡检请求发出后，如果接口 busy，则暂停当前 FSM 直到接口释放。

### 2.4 ECC 编解码复用

ECC 编解码直接复用 TCAM 维护读路径上的现有 ECC 解码器（用于读校验）和维护写路径上的 ECC 编码器（用于写保护）[^4]。巡检读到的数据经过 ECC 解码得到 syndrome 和错误标志，但硬件不执行纠错写回，仅上报。

### 2.5 中断与错误记录

错误记录采用 **分类型独立寄存器** 设计：

- **CE（1-bit 错误）寄存器组**：
  - `ERR_CE_BANK`：错误所在 Bank 号。
  - `ERR_CE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_CE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_CE_SYNDROME`：校正子。
  - `ERR_CE_BIT_POS`：错误位位置（用于软件定位修正）。
  - `ERR_CE_COUNT`：CE 累计错误次数（软件读清，用于监测硬件劣化趋势）。

- **UE（2-bit 错误）寄存器组**：
  - `ERR_UE_BANK`：错误所在 Bank 号。
  - `ERR_UE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_UE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_UE_SYNDROME`：校正子。

- **中断触发**：
  - `int0`：CE 检测到后立即触发，软件读清。
  - `int2`：UE 检测到后立即触发，软件读清。

- **锁存策略**：硬件采用 **先到先锁** 策略（锁存首个错误信息，后续错误被覆盖）。

- **CE 阈值告警**（可选）：当 `ERR_CE_COUNT` 超过可编程阈值时，可额外触发一次告警中断，提示硬件可能劣化。

> **注**：2-bit 错误（UE）触发 `int2` 致命中断，要求软件立即处理，不存在"累积计数再触发告警"的需求 [^6]，因此 UE **不配备独立计数器**。CE 则可以通过计数器累积，用于监测硬件劣化趋势。

### 2.6 校正子（Syndrome）与错误位位置（Bit Position）的关系

校正子（Syndrome）是 ECC 解码过程中产生的中间计算结果，等于新校验位与存储校验位的异或值 [^6]。对于 SEC-DED 码，校正子非零时指示存在错误：

- **CE 场景**：校正子非零，且其二进制值直接对应于出错比特的位置编号。硬件同时锁存 `ERR_CE_SYNDROME` 和 `ERR_CE_BIT_POS`，便于软件直接定位修正。
- **UE 场景**：校正子非零，但无法指示单一错误位置。硬件仅锁存 `ERR_UE_SYNDROME`，不提供 `ERR_UE_BIT_POS`（无此字段）。

虽然 Syndrome 和 Bit_Pos 在信息层面等价（Syndrome 就是错误位位置的二进制编码），但硬件保留两个字段的优势在于：
- 软件无需实现 Syndrome→Bit_Pos 查表转换，直接使用 Bit_Pos 修正即可
- 隔离软件与 ECC 编码实现细节，ECC 方案变更时硬件更新译码器即可，软件接口不变

## 3. 软件纠错流程

### 3.1 CE（1-bit 错误）处理流程

1. 中断服务程序（ISR）收到 `int0`，读取 CE 寄存器组确认错误信息。
2. 根据 `ERR_CE_BANK`、`ERR_CE_ARR_SEL` 和 `ERR_CE_ENTRY_ADDR`，通过维护接口读出完整的 entry 数据。
3. 软件根据 `ERR_CE_SYNDROME` 和 `ERR_CE_BIT_POS` 定位错误位，并修正（取反）。
4. 将修正后的数据通过维护接口写回原地址（需遵循 TCAM 写时序，Data 和 Mask 需分别写入 [^5]）。
5. 清除中断标志，可读取 `ERR_CE_COUNT` 判断是否需要告警。
6. 恢复巡检。

### 3.2 UE（2-bit 错误）处理流程

1. 中断服务程序（ISR）收到 `int2`，读取 UE 寄存器组确认错误信息。
2. 根据 `ERR_UE_BANK`、`ERR_UE_ARR_SEL` 和 `ERR_UE_ENTRY_ADDR` 定位错误位置。
3. 软件评估该条目的重要性，决定处理策略：
   - 若可重建 → 删除原条目，重新下发。
   - 若不可重建 → 标记该条目为无效，记录错误日志。
4. 清除中断标志，恢复巡检。

> **注意**：若同一个 entry 的 Data 和 Mask 均有错误，软件可在一次读操作中同时修正，分别写回 [^2]。UE 处理期间，软件应优先保证 `int2` 的中断响应延迟最小化。

## 4. 节流与定时控制

- **定时启动**：`PATROL_TIMER` 寄存器配置巡检启动间隔（以时钟周期为单位），超时后巡检自动开始一轮扫描。
- **空闲间隙**：每个 entry 的 Data 和 Mask 均校验完成后（即每轮 GAP），插入 `GAP_CYCLES` 个空闲周期（可配置），确保巡检不占满维护接口。
- **反压计数**：可选的 `BACKPRESSURE_CNT` 寄存器记录被反压的次数，供软件评估巡检效率。

## 5. 关键设计考虑

### 5.1 Data/Mask 独立校验

由于 Data 和 Mask 是独立的 SRAM 阵列，分别具有独立的 ECC 校验位 [^1]，因此巡检必须分别遍历两个阵列。每个 entry 的 ECC 域仅包含该阵列的存储位，不跨阵列。

### 5.2 写冲突的避免

本方案采用 **硬件检测 + 软件纠错**，硬件本身不执行写回，因此不存在巡检写与搜索的冲突问题 [^3]。软件纠错写入时，由 CPU 主动发起写操作，且 CPU 写优先级高于巡检读，软件可通过同步机制避免与搜索冲突。

### 5.3 错误窗口

从错误发生到软件完成纠错之间存在延迟（中断响应 + 软件处理），在此期间 **该 entry 可能被搜索命中并输出错误数据**。对于 CE 场景，单比特错误可能仍可容忍；对于 UE 场景，软件响应时间必须控制在系统容错范围内。建议将 `int2`（UE）的中断优先级设置为最高，确保快速响应。

- **无写冲突风险**：硬件不执行写回，由软件主动纠错，避免与搜索操作冲突 [^3]。
- **验证简化**：功能路径清晰，无复杂冲突仲裁逻辑。

## 一、优先级最低 ≠ 永远不需要节流

"优先级最低"解决的是**巡检与其他访问源的冲突仲裁问题**[^1]——当软件读写或搜索发生时，巡检被反压等待。但"TCAM 不工作"的场景并不等于"维护接口永远可用"，原因如下：

### 1. 维护接口可能被其他模块共享

TCAM 的维护接口通常不只被巡检控制器使用，还可能被以下源访问[^2]：
- 软件通过配置总线（如 APB/AXI-Lite）读写 TCAM 寄存器或 entry
- 硬件初始化流程（如 valid reset、flush 操作）
- 调试或诊断工具

即使 TCAM 没有搜索操作，这些访问仍然可能发生。如果巡检在没有任何间隙的情况下**连续占用维护接口**，软件或其他硬件模块可能在需要访问 TCAM 时被无限期阻塞。

### 2. 巡检 READ 本身也有延迟

每次巡检读取需要等待 ECC 解码完成，这个延迟是固定的[^3]。连续无间隙巡检意味着：
- 维护接口始终处于忙状态
- CPU 读 TCAM 寄存器的请求需要等待当前巡检 READ 完成
- 虽然 CPU 可以通过仲裁抢占，但频繁的抢占-释放会增加接口握手开销

## 二、间隙的作用：不仅是节流，更是"礼貌让步"

间隙的本质是**给维护接口一个空闲窗口**，让其他低优先级请求有机会被处理[^4]。具体来说：

| 场景 | 无间隙 | 有间隙 |
|:----|:-------|:-------|
| 巡检全速运行 | 维护接口 100% 被占用 | 接口有可编程的空闲时间片 |
| 软件突发访问 | 需等待当前 READ 完成 + 仲裁切换 | 间隙期间可直接发起访问 |
| 接口握手开销 | 每次抢占都需重新仲裁 | 减少仲裁切换次数 |

## 三、建议方案：保留间隙但允许配置为 0

保持 `GAP_CYCLES` 寄存器**可编程**，默认值为非零（如 4 个周期），但允许软件将其配置为 0：

- **配置为 0**：TCAM 完全空闲时，巡检连续运行，不留间隙（满足你想要的"一直检测"场景）
- **配置为非零**：在巡检性能与接口可用性之间取得平衡

这样既保留了灵活性，又允许极端情况下最大化巡检速度。但在默认配置中，建议保留一个较小的间隙值（如 1~4 个周期），避免接口被巡检独占。

| 最佳方案 | 保留可编程的 `GAP_CYCLES`，默认不为零，允许软件配置为 0 |

**ai**: # TCAM ECC 校验方案

## 1. 概述

本方案遵循 **硬件检测 + 软件纠错** 的设计思路。硬件负责后台巡检（Patrol Scrubbing）——定期遍历 TCAM 的 Data 阵列和 Mask 阵列，对每个条目进行 ECC 校验。当检测到错误时，根据错误类型上报不同等级的中断并锁存相关信息，由软件读取并修正数据。

TCAM 采用 Data/Mask 独立双阵列架构 [^1]，每个阵列的每个 entry 作为独立的 ECC 保护域。Data 阵列与 Mask 阵列深度相同，一一对应 [^2]。

### 中断分级

| 错误类型 | 中断等级 | 说明 |
|:--------:|:--------:|------|
| **1-bit 错误（CE）** | `int0`（普通中断） | 可纠正错误，软件可择机处理 |
| **2-bit 错误（UE）** | `int2`（致命中断） | 不可纠正错误，需软件立即响应处理 |

## 2. 硬件架构

### 2.1 巡检控制器 FSM

```
IDLE → READ_DATA → WAIT_DATA → CHECK_DATA → READ_MASK → WAIT_MASK → CHECK_MASK → GAP → ADDR_INC → IDLE/READ_DATA
```

- **IDLE**：等待 `patrol_enable` 且定时器超时（定时周期可编程）。
- **READ_DATA**：通过维护接口发出读请求，读取 Data 阵列当前 entry 的数据（Data+ECC）。
- **WAIT_DATA**：等待 Data 阵列读数据及 ECC 校验结果（syndrome）。
- **CHECK_DATA**：
  - 无错误 → 直接进入 READ_MASK。
  - **CE（1-bit 错误）** → 锁存错误信息（Bank、Data 阵列、entry 号、syndrome、错误位位置），触发 `int0`，进入 READ_MASK。
  - **UE（2-bit 错误）** → 锁存错误信息（Bank、Data 阵列、entry 号、syndrome），触发 `int2`，进入 READ_MASK。
- **READ_MASK**：通过维护接口发出读请求，读取 Mask 阵列当前 entry 的数据（Mask+ECC）。
- **WAIT_MASK**：等待 Mask 阵列读数据及 ECC 校验结果（syndrome）。
- **CHECK_MASK**：
  - 无错误 → 直接进入 GAP。
  - **CE（1-bit 错误）** → 锁存错误信息（Bank、Mask 阵列、entry 号、syndrome、错误位位置），触发 `int0`，进入 GAP。
  - **UE（2-bit 错误）** → 锁存错误信息（Bank、Mask 阵列、entry 号、syndrome），触发 `int2`，进入 GAP。
- **GAP**：插入可编程的空闲周期（节流控制）。
- **ADDR_INC**：递增 `entry_addr`，跳回 IDLE 或 READ_DATA。

> **设计说明**：对于同一个 index，先完成 Data 阵列校验，再完成 Mask 阵列校验，然后才更新地址。这种设计确保同一个 entry 的 Data 和 Mask 错误在同一轮巡检中被连续发现，有利于软件一次性处理 [^2]。

### 2.2 地址生成与遍历顺序

鉴于 Data 阵列和 Mask 阵列深度相同、一一对应 [^2]，地址生成器采用以下设计：

- **共用地址计数器**：维护一个 `entry_addr`（0 ~ N-1，N 为每个阵列的 entry 深度）。
- **阵列选择标志**：维护 1-bit `sel_arr`（0=Data，1=Mask），由 FSM 状态隐式控制，无需独立寄存器。
- **遍历顺序**：Data[0] → Mask[0] → Data[1] → Mask[1] → …… → Data[N-1] → Mask[N-1] → 回到 Data[0] 开始下一轮。
- **地址更新机制**：当前 entry 的 Data 和 Mask 均校验完成后（即 CHECK_MASK 状态结束后），`entry_addr` 递增。
- **可配置参数**：
  - 起始/终止地址（支持子区间巡检）。
  - 步长（支持跳过配置，例如每巡检 N 条跳过 M 条）。

### 2.3 优先级与反压机制

ECC 巡检的优先级在所有访问源中 **最低** [^3]，受以下约束：

- 当软件通过维护接口读写 TCAM 时，巡检 READ 请求被 **反压**（hold，等待接口释放后重新发出）。
- 当 TCAM 正在进行搜索操作时，巡检 READ 同样被反压。
- 当 TCAM 正在进行 valid reset、flush 等维护操作时，巡检 READ 被反压 [^5]。
- 巡检控制器在 IDLE 状态下持续检测维护接口的忙状态，仅当接口空闲时才启动 READ。
- 反压处理通过维护接口的 ready/valid 握手实现：巡检请求发出后，如果接口 busy，则暂停当前 FSM 直到接口释放。

### 2.4 ECC 编解码复用

ECC 编解码直接复用 TCAM 维护读路径上的现有 ECC 解码器（用于读校验）和维护写路径上的 ECC 编码器（用于写保护）[^4]。巡检读到的数据经过 ECC 解码得到 syndrome 和错误标志，但硬件不执行纠错写回，仅上报。

### 2.5 中断与错误记录

错误记录采用 **分类型独立寄存器** 设计：

- **CE（1-bit 错误）寄存器组**：
  - `ERR_CE_BANK`：错误所在 Bank 号。
  - `ERR_CE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_CE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_CE_SYNDROME`：校正子。
  - `ERR_CE_BIT_POS`：错误位位置（用于软件定位修正）。
  - `ERR_CE_COUNT`：CE 累计错误次数（软件读清，用于监测硬件劣化趋势）。

- **UE（2-bit 错误）寄存器组**：
  - `ERR_UE_BANK`：错误所在 Bank 号。
  - `ERR_UE_ARR_SEL`：错误所在阵列（0=Data，1=Mask）。
  - `ERR_UE_ENTRY_ADDR`：错误 entry 号。
  - `ERR_UE_SYNDROME`：校正子。

- **中断触发**：
  - `int0`：CE 检测到后立即触发，软件读清。
  - `int2`：UE 检测到后立即触发，软件读清。

- **锁存策略**：硬件采用 **先到先锁** 策略（锁存首个错误信息，后续错误被覆盖）。

- **CE 阈值告警**（可选）：当 `ERR_CE_COUNT` 超过可编程阈值时，可额外触发一次告警中断，提示硬件可能劣化。

> **注**：2-bit 错误（UE）触发 `int2` 致命中断，要求软件立即处理，不存在"累积计数再触发告警"的需求 [^6]，因此 UE **不配备独立计数器**。CE 则可以通过计数器累积，用于监测硬件劣化趋势。

### 2.6 校正子（Syndrome）与错误位位置（Bit Position）的关系

校正子（Syndrome）是 ECC 解码过程中产生的中间计算结果，等于新校验位与存储校验位的异或值 [^6]。对于 SEC-DED 码，校正子非零时指示存在错误：

- **CE 场景**：校正子非零，且其二进制值直接对应于出错比特的位置编号。硬件同时锁存 `ERR_CE_SYNDROME` 和 `ERR_CE_BIT_POS`，便于软件直接定位修正。
- **UE 场景**：校正子非零，但无法指示单一错误位置。硬件仅锁存 `ERR_UE_SYNDROME`，不提供 `ERR_UE_BIT_POS`（无此字段）。

虽然 Syndrome 和 Bit_Pos 在信息层面等价（Syndrome 就是错误位位置的二进制编码），但硬件保留两个字段的优势在于：
- 软件无需实现 Syndrome→Bit_Pos 查表转换，直接使用 Bit_Pos 修正即可
- 隔离软件与 ECC 编码实现细节，ECC 方案变更时硬件更新译码器即可，软件接口不变

## 3. 软件纠错流程

### 3.1 CE（1-bit 错误）处理流程

1. 中断服务程序（ISR）收到 `int0`，读取 CE 寄存器组确认错误信息。
2. 根据 `ERR_CE_BANK`、`ERR_CE_ARR_SEL` 和 `ERR_CE_ENTRY_ADDR`，通过维护接口读出完整的 entry 数据。
3. 软件根据 `ERR_CE_SYNDROME` 和 `ERR_CE_BIT_POS` 定位错误位，并修正（取反）。
4. 将修正后的数据通过维护接口写回原地址（需遵循 TCAM 写时序，Data 和 Mask 需分别写入 [^5]）。
5. 清除中断标志，可读取 `ERR_CE_COUNT` 判断是否需要告警。
6. 恢复巡检。

### 3.2 UE（2-bit 错误）处理流程

1. 中断服务程序（ISR）收到 `int2`，读取 UE 寄存器组确认错误信息。
2. 根据 `ERR_UE_BANK`、`ERR_UE_ARR_SEL` 和 `ERR_UE_ENTRY_ADDR` 定位错误位置。
3. 软件评估该条目的重要性，决定处理策略：
   - 若可重建 → 删除原条目，重新下发。
   - 若不可重建 → 标记该条目为无效，记录错误日志。
4. 清除中断标志，恢复巡检。

> **注意**：若同一个 entry 的 Data 和 Mask 均有错误，软件可在一次读操作中同时修正，分别写回 [^2]。UE 处理期间，软件应优先保证 `int2` 的中断响应延迟最小化。

## 4. 节流与定时控制

- **定时启动**：`PATROL_TIMER` 寄存器配置巡检启动间隔（以时钟周期为单位），超时后巡检自动开始一轮扫描。
- **空闲间隙**：`GAP_CYCLES` 寄存器保留，默认值为 0。由于巡检优先级最低，软件/搜索访问时会被自动反压，因此 TCAM 空闲时巡检可全速运行。仅在调试或功耗受限场景下，软件可将其配置为非零值以降低巡检速率。
- **反压计数**：可选的 `BACKPRESSURE_CNT` 寄存器记录被反压的次数，供软件评估巡检效率。

## 5. 关键设计考虑

### 5.1 Data/Mask 独立校验

由于 Data 和 Mask 是独立的 SRAM 阵列，分别具有独立的 ECC 校验位 [^1]，因此巡检必须分别遍历两个阵列。每个 entry 的 ECC 域仅包含该阵列的存储位，不跨阵列。

### 5.2 写冲突的避免

本方案采用 **硬件检测 + 软件纠错**，硬件本身不执行写回，因此不存在巡检写与搜索的冲突问题 [^3]。软件纠错写入时，由 CPU 主动发起写操作，且 CPU 写优先级高于巡检读，软件可通过同步机制避免与搜索冲突。

### 5.3 错误窗口

从错误发生到软件完成纠错之间存在延迟（中断响应 + 软件处理），在此期间 **该 entry 可能被搜索命中并输出错误数据**。对于 CE 场景，单比特错误可能仍可容忍；对于 UE 场景，软件响应时间必须控制在系统容错范围内。建议将 `int2`（UE）的中断优先级设置为最高，确保快速响应。

## 7. 方案优势

- **中断分级处理**：CE 使用 `int0` 普通中断，UE 使用 `int2` 致命中断，便于软件区分处理优先级 [^6]。
- **错误分类型独立记录**：CE 与 UE 使用独立的寄存器组，避免不同类型错误相互覆盖，软件处理逻辑更清晰。
- **CE 计数功能**：CE 累计计数器用于监测硬件劣化趋势；UE 无需计数，触发即立即处理 [^6]。
- **信息上报完整**：CE 上报 Bank、阵列、entry 号、syndrome 和错误位位置；UE 上报 Bank、阵列、entry 号和 syndrome。
- **逐 entry 连续校验**：同一 entry 的 Data 和 Mask 连续校验完成，便于软件一次性处理两个阵列的错误 [^2]。
- **硬件开销极小**：仅需巡检 FSM、共用地址计数器、1-bit 阵列选择和中断寄存器。
- **无写冲突风险**：硬件不执行写回，由软件主动纠错，避免与搜索操作冲突 [^3]。
- **验证简化**：功能路径清晰，无复杂冲突仲裁逻辑。
- **全速巡检**：GAP 默认 0，TCAM 空闲时巡检全速运行，最大限度地缩小错误发现窗口。
