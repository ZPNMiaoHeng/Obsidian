# CAP_POOL Action 表实现分析

## 1. 问题背景

- CAP_POOL 方案当前拆分为 32 个 Slice，Action 相关表为单张 SRAM 表。
- 32 个访问源存在同时访问 Action 表的冲突。

## 2. 当前方案

- 将 Action 表拆分为 32 个 Bank，每个访问源对应一个 Bank**。**
- **存在问题：** 部分表容量 < 64K，拆分为 32 Bank 后，单 Bank 容量 < 2K。按 SRAM 定制规则，小容量 SRAM 面积效率低，使用 Reg Table 实现更优**。**

## 3. 优化建议

- 对于容量 < 64K 的表，采用 **Reg Table** 实现，省去 Bank 拆分，可显著节省面积**。**
- 后端物理拥塞问题可在代码设计阶段通过合理布局规避**。**

## 4. 待决问题

表容量 ≥ 64K 的实现方案未确定，目前 Reg Table 查表延迟为 1 周期，SRAM 查表需要 3 周期，需评估对流水线的影响**。**

| 方案 | 适用范围 | 优点 | 缺点 |
|------|----------|------|------|
| **方案1**：放宽 Reg Table 上限至 128K | 容量 < 128K 的表 | Reg 延迟统一为 1-cycle | **ICAP_MISC_ACTIONS 表**（4K×170，680K）仍须 SRAM，其余表需等 2-cycle |

> **注：** 两种方案均涉及混合延迟场景，需结合模块时序和面积预算综合决策**。**

（要求：具体技术、方法、脚本、流程、避坑经验，明确复用点，禁止空话）

- **物理实现风险前移**  
  TCAM IP 采用寄存器搭建，布局布线时易因高扇入导致 `fanin` 问题。通过在编码阶段引入**寄存器复制**策略，显著缓解局部拥塞，可在 DC 综合阶段纳入 Checklist 项（如“检查寄存器 `fanin` 规模”），提前识别并规避。

- **存储定制预留灵活度**  
  MEM 定制时预留未使用的 bit，有效应对后续规格变动，避免因重新定制 MEM 引入过长周期。

**NTB 相关补充**  
![[CAP_POOl_action表实现分析]] 中关于 Action 表 Bank 拆分与 Reg/SRAM 选择的分析思路，可推广为小容量表统一使用 Reg Table 的通用策略，兼顾面积与延迟。

### 2. 本模块本次存在的不足 & 后续改进方案
（要求：避免自我否定，写具体遗漏、返工、场景缺失，每条配改进动作）

#### PRE_MC 模块

- **前期设计角度**  
  最初将 NT 组播窗口计算与 PCIE_ROUTE 组播窗口计算提前至 PRE_MC 实现，是为了规避 MCG 不一致问题。但该做法导致 PRE_MC 延迟从 **1‑cycle** 增至 **2‑cycle**，并引发了额外的时序压力。  
  由于后续确认 MCG 不一致仅需上报 `int0` 中断即可，原设计未能及时简化。

  **改进方案**  
  - NT MCG 计算后移至 **NT 组播路径**（该路径有 3‑cycle 空闲），普通组播 MCG 及不一致判断可放在 `pcie_route` 模块完成。  
  - 统一决策规则：**单拍表原则优先**，非必要不增加流水级。

#### NTB 模块

- **延迟资源利用不均**  
  NTB 最终延迟为 5‑cycle，NT 单播路径占用最大延迟，而 NT 组播路径存在 3‑cycle 空闲。未来设计中应主动规划**空闲周期复用**，将部分非关键计算填充到空闲 Path 中，减少整体流水线深度。

## 二、全流程视角复盘（团队 / 项目整体设计流程）

### 1. 现有流程中做得优秀、值得固化/深挖的环节
（需求→架构→文档→编码→仿真→联调→上机→闭环→协作，任一维度均可）

- **SystemVerilog 可综合语法推广**  
  项目编码中已使用 `logic` 替代 `wire/reg`，通过 `always_comb` 与 `always_ff` 显式区分组合逻辑与时序逻辑，显著减少综合歧义。建议固化为团队编码规范，在质量活动中强制推行。

### 2. 现有流程中不合理、卡顿、低效、需要优化的环节

- **质量活动中的跨组沟通**  
  文档汇总时，若超时未完成需逐一联系责任人，无法通过 Chat 确认对方是否已读消息，沟通效率低下。建议引入**自动提醒与状态跟踪**（如 Obsidian 任务插件 + 看板），降低人工催促成本。

- **前期需求/协议对齐滞后**  
  部分模块在协议细节（如 MCG 不一致处理）明确前已进入编码，导致后期返工。应强化**需求确认节点**，在架构设计阶段冻结关键异常场景的处理方案。

### 3. 个人对团队下一版迭代的建设性建议
（流程、规范、交付、用例、文档、自动化、协作机制均可）

- **统一提交要求**  
  1. 禁止流水账，只沉淀可复用、可改进、可落地内容  
  2. 亮点必须附带“推广价值”  
  3. 问题必须配“具体改进动作”  
  4. 聚焦：质量、效率、流程、技术沉淀  
  5. 截止时间：6.30 前输出

- **自动化检查链**  
  将 DC 综合的 `fanin` 检查、延迟约束（如单拍表 check）集成到 CI 流水线，实现前置风险拦截。

- **复盘闭环**  
  每次迭代问题需在下一版本架构评审时确认“改进动作落地”，避免重复踩坑。
