# CAP_POOL Action 表实现方案分析

![CAP_POOL Action 表实现分析](https://raw.githubusercontent.com/ZPNMiaoheng/picgo/main/1-CAP_POOl_action表实现分析.png)

## 1. 问题背景

- CAP_POOL 架构拆分为 32 个 Slice，每个 Slice 都会访问 Action 表。
- 当前 Action 表为**单张 SRAM 表**，32 个访问源存在并发冲突，需要解决访问问题。

## 2. 基础方案：Bank 拆分与存储介质选择

### 2.1 Bank 拆分方案

将 Action 表拆分为 32 个 Bank，每个 Slice 固定映射一个 Bank，消除访问冲突。

**存在的问题：**
- 部分表容量 < 64K，拆分为 32 Bank 后，单 Bank 深度可能小于 2K；
- SRAM 拆分到极浅深度后，每个 slice 对应的 selector 资源很少，面积效率低。

### 2.2 存储介质定制规则

根据项目 MEM 定制硬性规则：单 Bank 容量 ≤ 2K 时必须使用 Reg Table 实现；实际工程中，单 Bank 容量 < 4K 即推荐采用 Reg Table，因为小容量 SRAM 的面积开销不如 Reg Table 高效。

关键差异：
- **Reg Table**：延迟 **1 cycle**，无 ECC 校验，用户视角完全共享，布局布线可控。
- **SRAM Table**：延迟 **3 cycles**，需要 ECC 校验，面积优势随容量增大而显著（同等规格下 Reg Table 面积约为 SRAM 的 3 倍）。

## 3. 备选方案分析

### 方案 A：混合介质实现

- **ICAP Action 表**使用 **SRAM** 实现；
- **ECAP、VCAP Action 表**使用 **Reg Table** 实现。

**优点：**
- 大表发挥 SRAM 面积优势，小表利用 Reg 的低延迟和灵活性。

**缺点：**
- 混合介质增加了设计复杂度；
- Reg Table 部分可能存在物理拥塞风险，需在代码阶段通过复制寄存器等方式提前规避。

### 方案 B：纯 SRAM + 深度扩充

- 所有 Action 表均用 SRAM 实现；
- 拆分后若 Bank 深度过浅，将单 Bank 深度扩充至 **128**（参考 Meter 表实现）；
- 此时每个 Bank 作为**共享资源**，多个 Slice 通过寄存器分配访问，而非固定一对一绑定。

**优点：**
- 统一的 SRAM 存储，设计规整；
- 避免了极浅 SRAM 的面积浪费。

**缺点：**
- 所有访问都需要等待 SRAM 的 **3 cycle** 延迟；
- 小表（如 ECAP）同样被扩充到 128 深度，可能造成冗余。

**方案对比汇总：**

| 维度                | 方案 A                                 | 方案 B                                 |
|---------------------|----------------------------------------|----------------------------------------|
| 存储介质            | 混合（ICAP: SRAM, ECAP/VCAP: Reg）    | 全部 SRAM                              |
| 延迟                | ICAP: 3 cycles, 其他: 1 cycle          | 全部 3 cycles                          |
| 面积                | 大表用 SRAM 省面积，小表 Reg 面积适中  | 扩充后面积可能增大                     |
| 设计复杂度          | 混合时序，需处理两种接口               | 统一接口，较简单                       |
| 物理实现风险        | Reg 表需关注 fan-in 和拥塞             | 无特殊风险                              |
| 资源使用效率        | 小表 Reg 高效，大表 SRAM 高效          | 浅表扩充到 128 可能有浪费              |

## 4. 延迟与面积关键数据

- **Reg Table** 1 cycle 延迟，但同等规格下面积为 SRAM 的 3 倍（例如 1K×66 的表）。
- **SRAM Table** 3 cycle 延迟，拆分后若为 4K×66 且 32 Bank，单 Bank 仅 128×66（需加 ECC）。
- **混合延迟场景**：方案 A 中仅大表等 3 cycles，小表 1 cycle；方案 B 中所有表均等 3 cycles，相当于所有 Reg Table 必须等待 SRAM 表 2 个额外周期。

## 5. 决策建议

1. **优先使用 Reg Table 的场景**：当表容量较小（<4K）且访问频率极高、对延迟敏感时，Reg Table 是首选，其面积略大但时序更优。
2. **优选 SRAM 的场景**：当表容量较大（>4K）或 ECC 需求明确时，SRAM 的面积优势不可忽略。
3. **本模块实际评估**：
   - 需明确 ICAP、ECAP、VCAP 各 Action 表的规格（深度、宽度）及是否均 <4K。
   - 若 ECAP/VCAP 表规格很小（<2K），直接使用 Reg Table 是符合定制规则的硬性要求。
   - 若存在大表（>4K），则必须用 SRAM；此时再决定小表是否跟随 SRAM（方案 B）或混合（方案 A）。
   - 物理实现方面，Reg Table 的拥塞风险可通过寄存器复制和合理布局缓解，建议在 Checklist 中增加 DC 综合 fan-in 检查项。

## 6. 待决问题

- [ ] 各 Action 表的具体规格（深度、宽度）待确认。
- [ ] 面积和延迟预算需与后端/架构对齐。
- [ ] 若选择方案 A，需评估混合接口的时序收敛和验证复杂度。
- [ ] 若选择方案 B，需确认扩充深度后面积增量是否在预算内。

# CAP_POOL Action 表实现方案分析

![CAP_POOL Action 表实现分析](https://raw.githubusercontent.com/ZPNMiaoheng/picgo/main/1-CAP_POOl_action表实现分析.png)

## 1. 问题背景

CAP_POOL 方案拆分为 32 个 Slice，Action 相关表目前为单张 SRAM 表。32 个访问源存在同时访问 Action 表的冲突，需要将表拆分或重构以消除访问瓶颈[^1]。

## 2. 基础方案与问题分析

### 2.1 SRAM 拆分方案

将 Action 表拆分为 32 个 Bank，每个访问源对应一个 Bank，实现访问隔离。

**存在问题：**

- 部分表原始容量 < 64K，拆分为 32 Bank 后，单 Bank 容量不足 2K[^1]
- SRAM 拆分后 Bank 深度仅为 32，每个 Slice 对应的 Selector 数量太少，深度需扩充至 128 才能满足使用需求[^1]

### 2.2 存储介质选择原则

根据项目 MEM 定制规则，硬性要求单 Bank 容量 ≤ 2K 时采用 Reg Table 实现；实际工程中，单 Bank 容量 < 4K 均推荐采用 Reg Table，小容量 SRAM 的面积效率远不如 Reg Table[^1]。

## 3. 备选方案详析

### 方案 A：全 Reg Table 实现

所有 Action 表（ICAP、VCAP、ECAP）均使用 Reg Table 实现[^1]。

**优点：**

- 查表延迟统一为 **1 cycle**，无 ECC 校验开销
- 用户视角完全共享，使用灵活方便
- 可显著节省面积（针对小规格表）

**缺点：**

- Reg Table 物理实现存在拥塞风险，需在代码设计阶段通过寄存器复制、合理布局等方式提前规避，并需综合评估[^1]

---

### 方案 B：混合介质实现

- **VCAP、ECAP Action 表**使用 **Reg Table** 实现[^1]
- **ICAP Action 表**使用 **SRAM** 实现[^1]

**优点：**

- 大表发挥 SRAM 面积优势，小表利用 Reg Table 的低延迟与灵活性
- ECAP/VCAP 小表省去 Bank 拆分，实现简单

**缺点：**

- Reg Table 部分存在物理拥塞风险，需综合评估[^1]
- ICAP Action 中两个表深度需从 1K 扩充至 4K 以适配 SRAM Bank 拆分[^1]
- 混合介质增加设计复杂度，需处理两种接口时序

---

### 方案 C：纯 SRAM + 深度扩充

所有 Action 表统一采用 SRAM 实现[^1]。

- Bank 拆分后，深度统一扩充至 **128**（参考 Meter 表实现）[^1]
- 每个 Bank 作为**共享资源**，Slice 通过寄存器实现分配，而非固定一对一绑定[^1]

**优点：**

- 统一 SRAM 接口，设计规整，避免混合介质复杂度
- 无 Reg Table 物理拥塞风险

**缺点：**

- 所有表查表延迟均为 **3 cycles**，对小表不友好
- 扩充深度后，小表可能产生资源冗余

## 4. 关键参数对比

### 4.1 存储介质特性

| 特性 | Reg Table | SRAM Table |
|------|-----------|------------|
| 查表延迟 | **1 cycle** | **3 cycles** |
| ECC 校验 | 无需 | 需要 |
| 面积效率 | 小容量优势明显 | 大容量优势明显 |
| 物理风险 | 需规避拥塞 | 无特殊风险 |
| 使用灵活性 | 完全共享 | 需 Bank 管理 |

### 4.2 典型规格示例（1K × 66 表）

- **Reg Table**：直接实现 1K × 66 规格[^1]
- **SRAM**：需扩充至 4K × 66，拆分 32 Bank，单 Bank 规格 128 × 66，并额外考虑 ECC 校验位[^1]

### 4.3 面积参考

同等规格下，Reg Table 面积约为 SRAM 的 **3 倍**。若方案 B 中将 ICAP_MISC_ACTIONS 表改用 Reg 实现，其延迟可从 3-cycle 降至 1-cycle，但面积开销显著增加[^1]。

### 4.4 方案多维对比

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 存储介质 | 全部 Reg | 混合（ICAP: SRAM, 其他: Reg） | 全部 SRAM |
| 查表延迟 | 1 cycle | 混合（ICAP: 3 cycles, 其他: 1 cycle） | 3 cycles |
| 设计复杂度 | 低（统一接口） | 高（混合时序） | 中（统一接口，需共享管理） |
| 物理风险 | Reg 拥塞需规避 | Reg 拥塞需规避 | 无特殊风险 |
| 小表效率 | 高 | 高 | 低（扩充冗余） |
| 大表效率 | 面积开销大 | 高（SRAM 面积优势） | 高 |

## 5. 方案协同说明

### 5.1 定制规则与 64K 分界协同

Reg 定制规则（硬性 ≤ 2K → Reg，实际 < 4K → Reg）需与 64K 分界协同使用，避免小容量 Bank 因拆分后落入 Reg 约束内而降低使用效率[^1]。

### 5.2 混合延迟场景分析

- **方案 A**：无混合延迟，全 1-cycle
- **方案 B**：仅大表需等待 SRAM 的 3-cycle 输出，小表 1-cycle[^1]
- **方案 C**：所有 Reg Table 需等待 SRAM 表 2 个额外周期[^1]

需结合模块时序和面积预算综合决策[^1]。

## 6. 决策建议

1. **优先排除方案 C**：若小表容量明确 < 4K，SRAM 扩充到 128 深度既浪费面积又增加延迟，不符合定制规则的最优实践。

2. **大表存在时**：若 ICAP Action 表容量 ≥ 64K，SRAM 的面积优势不可忽略，此时应在方案 A 和方案 B 之间权衡：
   - 若 ICAP MISC_ACTIONS 表面积约束严格，选方案 B（该表用 SRAM）
   - 若对延迟一致性要求高或面积预算充裕，选方案 A（全 Reg，ICAP MISC_ACTIONS 也改用 Reg）

3. **无大表时**：若所有 Action 表均 < 4K，直接选方案 A（全 Reg Table），简单高效，符合 MEM 定制规则硬性要求。

4. **物理实现保障**：Reg Table 的拥塞风险可通过寄存器复制和合理布局缓解，建议在 Checklist 中增加 DC 综合 fan-in 检查项。
