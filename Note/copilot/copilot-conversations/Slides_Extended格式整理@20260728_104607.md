# Table（硬件表项）入门培训

## 1. 什么是“表（Table）”

### Slide Title
数字芯片中的 Table：核心数据结构的硬件载体

### Slide Content
- 问题：Table 在芯片中扮演什么角色？
- 核心三要素：
  - 容量（Depth × Width）：能存多少条目，每个条目多宽
  - 访问延迟：从发请求到拿结果需要几拍
  - 功耗与面积：芯片上的物理实现成本
- 培训目标：面对一个 Table，快速判断用 Reg、SRAM 还是 TCAM

### Speaker Notes
Table 用于存储配置信息、查找规则或中间结果。核心问题就是容量、延迟、面积三者的平衡。这次培训会用 5 个递进式问题带大家建立直觉。

## 2. 存储类型引导

### Slide Title
Step 1：小表 — Reg Table

### Slide Content
- 问题：8 条规则，每条 10 bit，最简单怎么实现？
- 答案：用 D 触发器（Flip-Flop）搭存储阵列
- 特点：
  - 查表延迟：**1-cycle**，速度最快
  - 可任意读写任意比特
  - ECC 校验：不需要，可靠性自然保证
  - 面积极大：每 bit ~20-24 个晶体管

```
D ❮═══╗     Q ❯
      ║
CLK ══╬═══
RST ══╝
  D Flip-Flop: ~20 transistors
```

### Speaker Notes
新人一般会用“把变量存数组”的思路。Reg 的问题不是功能，而是用昂贵的晶体管做存储，一次全读没问题，一百万个就爆炸。

---

### Slide Title
Step 2：容量问题 — 引入 SRAM

### Slide Content
- 问题：现在要存 100K × 64bit，Reg 方案还好吗？
- Reg 的后果：
  - 面积失控：~1.5 亿晶体管
  - 功耗爆炸：每拍全翻转
  - 布局拥塞：Reg 分散，后端布不开
- SRAM 解决方案：
  - 6T 交叉耦合锁存器，面积约为 Reg 的 1/3
  - 查表延迟：**3-cycle**（含流水线 + ECC 校验）

**工程经验：**
| 容量范围 | 推荐媒介 | 理由 |
|:---------|:---------|:-----|
| ≤ 2K | Reg | 硬性规则，面积可接受 |
| < 4K | Reg | 实际项目推荐，延迟优势关键 |
| > 2K | SRAM | 面积优势开始显现 |
| > 4K | SRAM | 建议批量使用 |

### Speaker Notes
核心：2K 是分水岭。4K 以下延迟优先用 Reg，4K 以上面积优先用 SRAM。

---

### Slide Title
Step 3：多访问源 — SRAM 端口类型

### Slide Content
- 问题：业务流水线和软件配置同时查表，一个接口不够咋办？
- SRAM 端口类型对比：
  - **SPRAM**（单端口）：1R 或 1W，面积最小功耗最低
  - **TPRAM**（双端口）：1R + 1W，读写可同时进行，面积适中
  - **DPRAM**（双端口）：2R/2W/1R1W，面积极大，灵活度最高

```
业务查表 ❯  Read Port   ┐
                          ┠ TPRAM (1R+1W)
CSR 配置 ❯  Write Port  ┘
```

- 核心：大部分项目用 SPRAM 最省；多源共享优先 TPARM；端口 > 2 加仲裁器

### Speaker Notes
多数表只有一个访问源（业务查表），所以 SPRAM 就够了。如果需要同时被查表和写配置，就用 TPRAM，读写各一路。三个以上的源，就必须加仲裁器了。

---

### Slide Title
Step 4：内容匹配 — 引入 CAM

### Slide Content
- 问题：防火墙规则表——不关心它在第几行，只想知道能不能过。输入数据，输出匹配结果——SRAM 能用吗？
- SRAM 的局限：你给我地址，我才给你数据
- CAM 的演进：你给我数据，我并行比较所有条目，返回命中结果
- 关键区别：CAM 只能做**精确匹配**——数据必须完全相等才命中

```
      SRAM                     CAM
    地址 ❯ ♢               Key ❯ ♢
   ┌──────────┐          ┌──────────┐
   │ [0] A    │          │ Entry 0  ❮ compare
   │ [1] B    │          │ Entry 1  ❮ compare
   │ [2] C    │          │ Entry 2  ❮ compare
   └────┬─────┘          └─────┬────┘
        ▼                      ▼
   返回数据                Hit/Miss + Index
```

### Speaker Notes
CAM 是一条一条比，把所有条目并行做“等于”运算。所以它能回答“有没有这个值”，但不能支持通配符。

---

### Slide Title
Step 5：模糊匹配 — 引入 TCAM

### Slide Content
- 问题：ACL 规则“允许 192.168.1.0/24”——前24位固定，后8位任意。CAM 能处理吗？
- TCAM 的诞生：每个 bit 可存三种状态——`0`、`1`、`X（Don't Care）`
- 内部双阵列架构：**Data 阵列 + Mask 阵列**

```
          Data Array    Mask Array
          ┌───┬───┐   ┌───┬───┐
Entry 0   │ 1 │ 0 │   │ 1 │ 0 │
          ├───┼───┤   ├───┼───┤
Entry 1   │ 0 │ 1 │   │ 0 │ 1 │
          └───┴───┘   └───┴───┘
```

- 编码规则：
| Data | Mask | 含义 | 
|:----:|:----:|:-----|
| 0 | 0 | X (Don't Care)，忽略 |
| 0 | 1 | 0，必须匹配 0 |
| 1 | 0 | 1，必须匹配 1 |
| 1 | 1 | 禁止状态 |
- 匹配逻辑：`Match = (Data ^ Key) & Mask`
- 特性：并行匹配 1-2 cycle，面积极大，管理复杂

### Speaker Notes
TCAM 是唯一能并行做模糊匹配的介质。但它用两个阵列存一位，面积惊人。项目中只在最关键的路径（如 ACL 查表）才用，不能乱用。

## 3. 功能专题

### Slide Title
专题一：仲裁器 — 当端口数 > 2 时

### Slide Content
- 问题：一张表一个物理接口，业务查表、CSR 配置、ECC 巡检三个源都要用，怎么办？
- 仲裁器（Arbiter）：多个源竞争一个共享接口时，按优先级或轮询分配访问权
- 常用优先级策略：
  - **ECC 回写**（最高）：纠错操作时效性高，发生概率极低
  - **CSR 配置**（中等）：配置响应需及时
  - **业务查表**（最低）：可通过流水线缓冲等待
- 设计成本：仲裁器引入会额外增加 **1-cycle 延迟**
- TCAM 注意：维护接口（写/读/FLUSH）是单通道串行，仲裁器必须确保同一时刻只有一路源在使用

```
源A（查表）❯
源B（CSR）❯   ❮ Arbiter ❯  ➡   SRAM/TCAM
源C（ECC）❯          优先级：ECC > CSR > 查表
```

### Speaker Notes
固定优先级硬件开销小，工程上最常用。低优先级源不会永远被阻塞：ECC 极端稀少，CSR 只偶尔发生，查表流水线有缓冲，响应 OK。

---

### Slide Title
专题二：Bank 拆分 — 当单块 SRAM 规格过大时

### Slide Content
- 问题：一张深 32K 的 SRAM 表，单块 SRAM IP 不支持，怎么办？
- 方案：按深度拆分成多个 Bank，地址高 bit 选 Bank
- 收益维度：
  - 绕过 IP 限制，突破单块深度/宽度上限
  - 降低动态功耗：每次只激活 1 个 Bank
  - 提升工作频率：更短的位线，减少寄生负载
  - 提升访问带宽：不同 Bank 可并行响应不同请求
- 代价维度：
  - 总面积增大：每个 Bank 需独立译码器、灵敏放大器
  - 漏电功耗增加：更多晶体管处于待机状态
  - 需要地址译码器和数据选择 MUX

```
地址 ❯  Bank Select (addr[high])
     ┌──┬──┬──┬──┐
     │B0│B1│B2│B3│
     └┬─┴┬─┴┬─┴┬─┘
      ▼  ▼  ▼  ▼  ← 只有选中 Bank 激活
```

- 工程经验：“拆一半”（N=2）是最常见折中点；N > 4 时负面效应非线性加剧
- 注意：单 Bank 深度 < 2K 时，SRAM 相对 Reg 无优势，建议改用 Reg

### Speaker Notes
Bank 不是越多越好。2~4 bank 是 sweet spot。超过 4 bank，外围电路占比太大，总面积可能反而超过单块大 SRAM。每次只激活 1 个 bank，这是降低功耗的关键。

## 4. 安全与可靠性专题

### Slide Title
SRAM ECC 校验

### Slide Content
- 背景：先进工艺下 SRAM 易受粒子撞击导致数据翻转（SEU）
- ECC 逻辑在 SRAM IP **外部**实现，通过 Wrapper 封装
- 校验延迟是 SRAM 3-cycle 的主要原因之一
- 错误处理策略：
  - 1bit 错误 → 硬件自动纠正 + 回写 + 上报错误 Bank 号
  - 2bit 错误 → 触发高级别中断，等待软件介入（硬件无法纠正）
- 核心原则：SRAM 必配 ECC，这是芯片稳定性的基本保障

### Speaker Notes
ECC 是不可省的基础保护。1bit 硬件能自动修；2bit 交软件处理。不需要打碎设计——在 Wrapper 层做封装即可。

---

### Slide Title
TCAM 禁止编码

### Slide Content
- 核心禁区：**Data=1, Mask=1** — 软件绝对禁止写入
- 可能后果：
  - 内部电路工作异常（短路、过大电流风险）
  - 输出不定态（X）
  - 功能级错误（误匹配或漏匹配）
- 原则：软件写入 TCAM 时，必须保证 Data+Mask ≠ 11
- 工程检查点：设计文档中明确标记此约束，代码中添加断言或保护逻辑

### Speaker Notes
这个规定是芯片级的。一旦误写入了 11，芯片会出 X 态。所以必须前置检查，靠硬件保护或软件约束杜绝。

## 5. 整体培训流程建议

### Slide Title
推荐培训流程

### Slide Content
- **1. 开门见山 — 什么是 Table？**（5 min）
  - 数组/哈希表 → 硬件实现
- **2. 问题链引导**（30 min）
  - Step 1：小表 → Reg Table
  - Step 2：容量问题 → SRAM
  - Step 3：多源访问 → SPRAM/TPRAM/DPRAM
  - Step 4：内容匹配 → CAM
  - Step 5：模糊匹配 → TCAM
- **3. 功能专题**（20 min）
  - 专题一：仲裁器（原理 + 优先级策略 + 实现）
  - 专题二：Bank 拆分（收益 + 代价 + 经验值）
- **4. 安全与可靠性**（10 min）
  - SRAM 必配 ECC
  - TCAM 避免 11 编码
  - 地址不能超限，初始化未完成读返回 0
- **5. Q&A**（5 min）

### Speaker Notes
总时长约 70 min。每一节都有递进式问题驱动，学员跟着“发现痛点-找到方案”的路径走，完成整场培训。

## 6. 项目避坑经验

### Slide Title
实战必读

### Slide Content
1. **小表不要强行定制 SRAM**：容量 < 2K 时，SRAM 相对 Reg 无面积优势，直接用 Reg 更稳妥
2. **SRAM 必配 ECC**：稳定性的基本保障
3. **TCAM 编码安全**：软件绝对避免写入 Data=1, Mask=1 的禁止编码
4. **地址合法性**：读写表地址不能超过规格深度，超限可能返回 X 态
5. **初始化**：所有 Table 上电后需软件初始化，完成前读返回 0

### Speaker Notes
经验教训：有的项目图省事小表也用了 SRAM，结果面积还大了；有的 SRAM 没配 ECC，芯片现场出了间歇性故障。这 5 条就是最低要求，每一条都有真实教训。
