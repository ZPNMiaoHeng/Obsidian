# Table（硬件表项）入门培训

## 1. 培训目的

- 了解芯片设计中“表（Table）”的概念和用途。
- 掌握三种核心存储实现方式：**Reg Table（寄存器表）**、**SRAM Table（静态随机存取存储器表）**、**TCAM（三态内容寻址存储器）** 的基本原理、特点及适用场景。
- 了解项目中的基本设计规则和定制经验，避免后续开发踩坑。

---

## 2. 什么是“表（Table）”？

在数字芯片中，**Table** 是核心数据结构的载体，用于存储芯片运行的配置信息、查找规则或中间结果。它和我们日常编程使用的“数组”或“哈希表”类似。

当有输入请求时，芯片通过一个特定的 **Key（索引键值）** 查找 Table，并返回一个对应的 **Data（结果数据）**。这个过程无处不在，比如：

- 路由器查找下一跳地址[^1]。
- 防火墙匹配 **ACL（访问控制列表）** 规则[^2]。
- 内部模块间的 ID 映射或状态机记录。

**核心三要素：**
- **容量（深度 Depth × 宽度 Width）**：表能存放多少条目，以及每个条目的数据位宽。
- **访问延迟**：从发出查找请求到拿到结果需要的时钟周期数。
- **功耗与面积**：在芯片上物理实现的成本。

Table 可以用不同的“物理材料”来实现，**Reg Table**、**SRAM 和 TCAM** 是我们最常用的三种。

---

## 3. Reg Table（寄存器表）

### 3.1 什么是 Reg Table？

Reg Table 就是用基本的 **D 触发器（Flip-Flop）** 搭建出来的存储阵列。你可以把它想象成一个由成千上万个“小开关”拼成的巨大单元格。

### 3.2 核心特点

- **延迟低**：查表延迟固定为 **1 Cycle**，速度极快[^1]。
- **访问灵活**：可以任意读写任意比特，非常自由。
- **无校验成本**：通常情况下，Reg Table 不需要复杂的 **ECC（错误检查和纠正）** 逻辑来保证数据可靠性[^1]。
- **面积劣势**：与 SRAM 相比，同等容量下 Reg Table 的面积要大得多（约 **3倍**）[^1]。

### 3.3 什么时候用？——小容量表

因为面积大，所以 Reg Table 主要用在容量很小、但对延迟要求高的场景。

**项目中的经验准则是：**

- **硬性规则**：容量 ≤ **2K** 时，强制使用 Reg Table[^1]。
- **实际参考**：在项目中，通常容量 < **4K** 时，比较推荐使用 Reg Table[^1]。

### 3.4 应用场景

- **Private Table**：容量小、访问频繁的表，例如每条流水线自己用的独立状态缓存[^1]。
- **控制寄存器**：芯片的配置信息，可以用 Reg 实现。
- **小索引表**：比如一个只有 8 个条目的**优先级映射表**。

---

## 4. SRAM Table（静态随机存取存储器）

### 4.1 什么是 SRAM？

SRAM 是一种标准的存储单元阵列，由专用的 **SRAM IP 编译器** 生成。它是芯片中最主要的存储载体，平衡了面积和速度。

> 可以把 Reg Table 视为“机动部队”，灵活但昂贵；SRAM 是“大部队”，专业高效，但需要点时间调度。

### 4.2 核⼼特点

- **大容量，面积优**：SRAM 是存储大容量数据最经济的硬件实现方式。
- **延迟中等**：查表延迟通常为 **3 Cycles**（包含输出流水线和校验开销）[^1]。
- **结构固定**：SRAM 有固定的物理结构，地址、数据、控制信号必须按照规定时序驱动。
- **需要校验**：SRAM 在先进工艺下容易受粒子撞击等影响导致数据翻转（**SEU**），需要 **ECC** 保护。ECC 校验带来的额外延迟是导致 3-cycle 查表的主要原因之一[^1]。
- **支持写掩码**：SRAM 通常支持 **写掩码**，即可以只更新一个字（Entry）中的某几个比特[^3]。

### 4.3 什么时候用？——大容量表

**项目中的经验准则是：**

- 当容量 **> 2K** 时，SRAM 在面积上开始有优势[^1]。
- 建议在容量 > **4K** 时，批量使用 SRAM 来实现。

### 4.4 ⼯程要点

1.  **Bank拆分**：单块 SRAM 容量过大会导致时序变差、功耗过高。通常采用 **按深度拆分** 策略，把一张大表拆成多个 Bank。
    - **收益**：降低单位查表功耗（只激活一个 Bank）、提升工作频率（位线更短）、绕过 IP 极限[^4]。
    - **代价**：总面积稍增、漏电功耗（Leakage）增大[^4]。
    - **经验值**：“拆一半”通常是效果不错的折中点[^4]。
2.  **初始化**：SRAM 上电后的值是随机的。芯片刚上电后，软件需要通过写操作对 SRAM 进行初始化赋值。初始化完成前，对未完成表的读操作返回 **0**[^5]。

## 5. TCAM（三态内容寻址存储器）

### 5.1 什么是 TCAM？

这是 Table 中的“特种兵”。普通 Table 是“我给你地址，你返回数据”；TCAM 是“我给你数据，你返回地址”，并且它是**并行**的，速度快得惊人。

它之所以叫“三态”，是因为它的每个比特（bit）可以存储三种状态：`0`、`1` 和 `X（Don't Care，忽略）`[^1]。

> 举个ACL场景的例子：有 100 条规则（例如规则 1 是 `允许IP 192.168.1.0/24`），来了一个数据包。如果用普通方法，需要逐条去比对。而 TCAM 可以在 1～2 个时钟周期内，并行地帮你在 100 条规则里找到匹配的那一条。

### 5.2 工作原理

TCAM 内部通常由两个独立的阵列组成：**Data 阵列** 和 **Mask 阵列**[^6]。

- **Data**：存储对比的目标值。
- **Mask**：存储“掩码”，标记哪些位需要比，哪些位可以忽略。

编码方式如下：

| Data | Mask | 含义 |
|:----:|:----:|:----:|
| 0 | 0 | **Don't Care**：比较时忽略该位 |
| 0 | 1 | **0**：必须匹配 0 |
| 1 | 0 | **1**：必须匹配 1 |
| 1 | 1 | **Prohibited**：禁止状态，一般不允许出现 |

其匹配逻辑可以理解为：

```verilog
// 匹配信号 = (输入的 Key 异或上存储的Data) 再与上存储的Mask
Match = (Data ^ Key) & Mask;
// 如果Mask(对应位) = 0，那么不管Data和Key是否相等，(Data ^ Key) & 0 恒等于 0，表示该位“自动匹配”。
```

### 5.3 Valid Bit

每个 TCAM 条目还会独立存在一个 **Valid Bit**，用来标记该条目是否有效[^6]。

- **作用**：
    - **快速清空**：可以通过全局引脚 `RST/FLUSH` 瞬间把所有 Valid 位清零（批量复位），而不需要逐个去清除每个条目的 Data 和 Mask 数据[^7]。
    - **功耗优化**：在搜索时，如果 Valid Bit 为 0，该条目的比较逻辑可以被旁路或者动态门控，从而省电。

### 5.4 特点与选择合适的存储介质

- **核心优势**：**极快的并行匹配速度**，通常能在 1-2 个时钟周期返回匹配结果。支持模糊匹配（**Wildcard**）。
- **核心劣势**：
    - **面积极大**：比 SRAM 和 Reg Table 都大，而且贵。项目中只在极其关键的路径上使用。
    - **功耗较高**：每次都并行使能，尤其是高速场景下功耗会比较高。
    - **管理复杂**：不支持随机写Entry（可能会破坏其他表的连接关系），通常需要专门的搬移和清空逻辑[^8]。

### 5.5 什么时候用？（0经验速查表）

以下是给你的一个速查表，可以帮你快速判断在面对一个Table需求时，应该使用哪种存储介质：

| 需求场景 | 推荐媒介 | 核心理由 |
| :--- | :--- | :--- |
| 容量 **< 2K**，且需要**1拍**出结果 | **Reg Table** | 面积小到可以忽略，延迟最低，无校验开销[^1]。 |
| 容量 **> 4K**，只需精确匹配 | **SRAM** | 面积最优，适合大容量存储，ECC 保证可靠性[^1]。 |
| 需要**模糊匹配** (Wildcard)，如 ACL | **TCAM** | 唯一能并行完成此功能的选择[^1]。 |
| 某表同时被多个模块访问 | **SRAM** (多端口) | 普通 SRAM 通过分时调度或双口 IP 实现多端口共享。 |

## 6. 总结与关键设计原则

1.  **目标导向**：通常，如果一个 Table 可以用 Reg 实现，就不用 SRAM；能用 SRAM，就不用 TCAM。反过来，如果容量太大或者需要并行匹配，就只能选后面的。
2.  **延迟与流水**：Reg Table 1-cycle（周期），SRAM Table 通常是 3-cycle，TCAM 的读操作需要 1-2 个周期，但搜索操作非常快[^1]。
3.  **安全第一**：
    - **SRAM 必配 ECC**：大容量 SRAM 必须加上 **ECC 保护**，这是芯片稳定性的基本保障。
    - **TCAM 告警**：**Data=1, Mask=1** 的编码在大多数支持写入掩码的 TCAM IP 中是 **禁止状态**，软件需绝对避免写入，否则可能导致严重功能错误甚至物理损坏。
4.  **CPU访问**：软件通过 **CSR（配置状态寄存器）** 读写 Table 时，需要考虑**同步**和**仲裁**。CSR 路径表读写会占用查表的物理接口，如果软件持续操作，可能会阻塞业务查表。
5.  **初始化**：所有 Table 都需要在上电后进行初始化（SRAM/TCAM 由软件写入，Reg 可以通过复位信号置位）。初始化完成前，读返回 **0**，业务如果提前发起查表请求，需要保证这不会引起问题[^5]。
6.  **地址合法性**：**读写表的地址不能超过其规格深度**。访问超出表有效范围的地址，未初始化时读操作可能返回 `x`（不定态），导致仿真和后端验证出现问题[^5]。软件必须保证地址有效。

## 7. 项目避坑经验

- **过定制：** 不要对小表（例如小于 2K）去定制 SRAM。为了省一点面积，带来的定制周期和流片风险其实不划算。**直接上 Reg Table 更稳妥**[^1]。
- **拆分规则：** 把大 SRAM 表拆成 Bank 是一种降低动态功耗、提高时序的好方法。但 **Bank 数量不是越多越好**。拆得太多，面积和漏电会剧增。记住，拆到一半左右（N=2）通常是效果较好且代价较小的[^4]。
- **预留冗余**：在定制 MEM（包括 SRAM 和 TCAM）时，如果条件允许，**预留一些未使用的比特（Spare Bit）**。这不会增加太多面积，但能非常方便地应对未来规格的小幅调整（例如增加一个字段），避免因重新定制 MEM 投入大量时间[^9]。
- **读写互斥**：一组 Table 接口，在一个时钟周期内**只能响应读或写**。如果同时有效，硬件通常只会响应**写操作**[^5]。软件在编程时要考虑这一点，不能同时进行读写。

### 4.5 补充工程要点

以下三点是实际项目中使用 SRAM 时必须掌握的核心概念：

#### 4.5.1 选 Bank 操作

当一张大 SRAM 表按深度拆分为多个 Bank 后，**每次查表都需要先选出目标 Bank**。

- 查表请求到达时，硬件根据查表地址的高位（或低位，取决于地址映射策略）进行译码，生成 Bank 选择信号，仅激活对应的 Bank[^4]。
- **未被选中的 Bank 保持休眠状态**，不参与本次读写，从而实现动态功耗的降低。
- 选 Bank 操作也会引入额外的控制逻辑开销，例如 Bank 译码器、数据选择 MUX 等，但这些逻辑的开销远小于 Bank 使能带来的功耗收益[^4]。

#### 4.5.2 多访问源仲裁

当 SRAM 表需要被多个访问源（例如业务流水线查表、软件 CSR 配置写表、ECC 巡检回写等）共享时，就需要引入**仲裁器**。

- **仲裁规则**：不同访问源在同一时钟周期发起请求时，仲裁器按优先级决定哪个源获得该时钟周期的访问权。以项目经验为例，ECC 回写操作的优先级通常最高，CSR 配置访问次之，业务流水线查表的优先级相对较低[^3]。
- **实现方案**：常用的仲裁策略有**固定优先级**和**轮询（Round-Robin）** 两种。固定优先级硬件开销小，但低优先级源可能被长期阻塞；轮询则能提供相对公平的带宽分配[^1]。
- **设计要点**：仲裁器的引入意味着查表延迟会因等待仲裁而**额外增加 1 拍**，在评估流水线级数时需考虑此因素。

#### 4.5.3 晶体管级面积对比：SRAM vs Reg

从晶体管搭建的物理层次来看，**每 1 bit SRAM 的面积约为 Reg 类型的 1/3**[^1]。

- **根源**：SRAM 的存储单元使用 **6 个晶体管（6T）** 组成一个交叉耦合锁存器，而 Reg（D 触发器）则需要约 **20～24 个晶体管**来实现存储+输入输出控制逻辑。
- **工程含义**：这解释了为什么容量 < 2K 时推荐使用 Reg Table（Reg 的灵活性和 1-cycle 延迟优势远大于其面积劣势），而容量 > 2K 时 SRAM 的面积优势开始显现，并在 > 4K 后成为绝对的经济选择[^1]。
- **注意**：这里的面积对比仅指**存储阵列本身**。实际芯片中，SRAM 还需要计入外围电路（译码器、灵敏放大器、ECC 校验逻辑等）的面积开销，但这些外围电路的总面积占比在容量足够大时会变得很小，不影响 SRAM 的整体面积优势。

## 5.7 TCAM 多访问源仲裁

TCAM 同样存在多访问源共享同一组物理接口的情况，需要引入仲裁逻辑。

**常见的访问源：**
- 业务搜索请求（流水线发起的 lookup）
- 软件通过 CSR 配置进行条目读写
- ECC 巡检或回写操作（若有 ECC 保护，详见 5.8 节）
- 数据搬移或清空操作

**仲裁策略：**

| 来源 | 典型优先级 | 说明 |
|------|:----------:|------|
| ECC 回写 | **最高** | 纠错操作的时效性要求高，且发生概率极低，反压业务不影响整体性能[^1] |
| 软件 CSR 读写 | **较高** | 配置响应需要及时，通常硬件会保证 CSR 操作不被业务长期阻塞[^2] |
| 业务搜索请求 | **较低** | 搜索可通过流水线缓冲等待仲裁，对微短时反压容忍度较高 |

**注意**：TCAM 的维护接口（写条目、读条目、批量 FLUSH 等）一般是**单通道串行**的，仲裁器需要确保同一时刻只有一路访问源在使用该接口，否则会导致数据错乱[^3]。

## 5.8 TCAM ECC 校验：为什么实现在 IP 外围？

### 5.8.1 为什么不在 IP 内部做？

商用 TCAM IP 通常**仅提供原始的存储阵列**（Data 阵列 + Mask 阵列），而不集成完整的 ECC 编解码与回写逻辑，原因如下：

1. **通用性考虑**：IP 供应商为了保持产品的通用性，不会绑定特定的 ECC 策略。不同客户对 ECC 的纠错能力（SEC / SECDED）、巡检策略、回写方式（软件介入 vs. 硬件自动）需求各异，将 ECC 放在外部有利于客户按需定制[^4]。

2. **Data/Mask 独立校验需求**：TCAM 的 Data 阵列和 Mask 阵列是物理独立的 SRAM 阵列，需要**分别独立计算 ECC 校验位**。若在 IP 内部集成，意味着需要为两个阵列分别设计两套编解码逻辑，增加了 IP 的复杂度和面积[^1]。

3. **巡检与回写控制**：巡检（Scrubbing）需要控制器按地址遍历所有条目、触发读写、检查纠错并决定是否回写。这类状态机逻辑若嵌入 IP 内部，会固化 IP 的控制流程，降低灵活性。放在外围则可以用标准 RTL 灵活实现[^1]。

### 5.8.2 外部实现方案

外部实现的 ECC Wrapper 结构如下：

```
+-----------------------+
|   ECC Wrapper (外围)    |
|  +-----+  +--------+   |
|  | ECC |  | 巡检控制器 |   |
|  |编解码|  | (FSM)  |   |
|  +--+--+  +----+---+   |
|     |           |       |
+-----+-----------+-------+
      |           |
      v           v
+-----+-----+   +--+--+
| TCAM IP   |   | ECC   |
| Data+Mask |   |校验位  |
| 阵列      |   | SRAM  |
+-----------+   +------+
```

**核心要点：**

- **ECC 校验位存储**：在 IP 外部实例化一个带写掩码的独立 SRAM，用于存储 Data 和 Mask 阵列的 ECC 校验位。该 SRAM 本身**不额外做 ECC 校验**（因为它本身规模小，且 ECC 校验位出错概率极低）[^5]。
- **独立校验，统一存储**：Data 阵列与 Mask 阵列分别独立计算 ECC 校验位，但校验位统一存储在同一块外部 SRAM 中，通过写掩码控制只更新某一阵列对应的校验位[^6]。
- **硬件自动回写**：巡检或正常读操作发现 1-bit 错误后，硬件自动纠正并写回原地址，同时通过写掩码仅更新对应阵列的校验位部分。回写优先级最高，可反压业务流水线[^1]。

**巡检流程（FSM）：**

```
IDLE → [计数器翻转] → READ_DATA → CHECK_DATA → READ_MASK → CHECK_MASK → ADDR_INC → IDLE
                        ↓ (CE)            ↓ (CE)
                     [WRITE_BACK]      [WRITE_BACK]
```

- **READ_DATA / READ_MASK**：通过 TCAM 维护接口读当前条目，同时从外部 SRAM 读对应校验位。
- **CHECK_DATA / CHECK_MASK**：ECC 解码，判断是否发生错误。
  - CE（1-bit 错误）→ 进入 WRITE_BACK 状态，自动纠正并写回，同时上报出错地址和 bank 号。
  - UE（2-bit 错误）→ 锁存错误信息，触发高级别中断，等待软件介入[^7]。
- **巡检读优先级最低**：当 TCAM 正在执行搜索、软件 CSR 操作或 FLUSH 等维护操作时，巡检读被反压等待，避免影响正常业务[^8]。

# Table（硬件表项）入门培训（优化版）

## 1. 培训目的

- 了解芯片设计中"表（Table）"的概念和用途。
- 掌握三种核心存储实现方式：**Reg Table（寄存器表）**、**SRAM Table（静态随机存取存储器表）**、**TCAM（三态内容寻址存储器）** 的基本原理、特点及适用场景。
- 了解项目中的基本设计规则和定制经验，避免后续开发踩坑。

---

## 2. 什么是"表（Table）"？

在数字芯片中，**Table** 是核心数据结构的载体，用于存储芯片运行的配置信息、查找规则或中间结果。它和我们日常编程使用的"数组"或"哈希表"类似。

```
           输入 Key（索引）
                │
                ▼
        ┌───────────────┐
        │   Table       │
        │  ┌───┬───┐   │
        │  │ 0 │ A │   │
        │  ├───┼───┤   │
        │  │ 1 │ B │   │
        │  ├───┼───┤   │
        │  │ 2 │ C │   │
        │  └───┴───┘   │
        └───────┬───────┘
                │
                ▼
         返回 Data（结果数据）
```

**核心三要素：**
- **容量（深度 Depth × 宽度 Width）**：表能存放多少条目，以及每个条目的数据位宽。
- **访问延迟**：从发出查找请求到拿到结果需要的时钟周期数。
- **功耗与面积**：在芯片上物理实现的成本。

---

## 3. Reg Table（寄存器表）

### 3.1 什么是 Reg Table？

Reg Table 就是用基本的 **D 触发器（Flip-Flop）** 搭建出来的存储阵列。你可以把它想象成一个由成千上万个"小开关"拼成的巨大单元格。

```
  Reg 存储单元（D 触发器）
  ┌────────────────────┐
  │                    │
  │   D ────┬──── Q    │
  │         │          │
  │  CLK ───┤          │
  │         │          │
  │  RST ───┘          │
  │                    │
  │  ~20~24 个晶体管    │
  └────────────────────┘
```

### 3.2 核心特点

- **延迟低**：查表延迟固定为 **1 Cycle**，速度极快。
- **访问灵活**：可以任意读写任意比特，非常自由。
- **无校验成本**：通常情况下，Reg Table 不需要复杂的 **ECC（错误检查和纠正）** 逻辑来保证数据可靠性。
- **面积劣势**：与 SRAM 相比，同等容量下 Reg Table 的面积要大得多（约 **3倍**）。

### 3.3 什么时候用？——小容量表

因为面积大，所以 Reg Table 主要用在容量很小、但对延迟要求高的场景。

**项目中的经验准则是：**

- **硬性规则**：容量 ≤ **2K** 时，强制使用 Reg Table。
- **实际参考**：在项目中，通常容量 < **4K** 时，比较推荐使用 Reg Table。

---

## 4. SRAM Table（静态随机存取存储器）

### 4.1 什么是 SRAM？

SRAM 是一种标准的存储单元阵列，由专用的 **SRAM IP 编译器** 生成。它是芯片中最主要的存储载体，平衡了面积和速度。

> 可以把 Reg Table 视为"机动部队"，灵活但昂贵；SRAM 是"大部队"，专业高效，但需要点时间调度。

```
  SRAM 存储单元（6T 结构）
  ┌──────────────────────┐
  │                      │
  │      VDD             │
  │       │              │
  │   ┌───┴───┐          │
  │   │       │          │
  │   └───┬───┘          │
  │       │              │
  │   ┌───┴───┐          │
  │   │       │          │
  │   └───┬───┘          │
  │       │              │
  │      GND             │
  │                      │
  │      ~6 个晶体管      │
  └──────────────────────┘
```

### 4.2 核心特点

- **大容量，面积优**：SRAM 是存储大容量数据最经济的硬件实现方式。
- **延迟中等**：查表延迟通常为 **3 Cycles**（包含输出流水线和校验开销）。
- **结构固定**：SRAM 有固定的物理结构，地址、数据、控制信号必须按照规定时序驱动。
- **需要校验**：SRAM 在先进工艺下容易受粒子撞击等影响导致数据翻转（**SEU**），需要 **ECC** 保护。
- **支持写掩码**：SRAM 通常支持 **写掩码**，即可以只更新一个字（Entry）中的某几个比特。

### 4.3 晶体管级面积对比：SRAM vs Reg

```
面积比 = 3 : 1（同等容量下 Reg : SRAM）

  Reg 存储单元                    SRAM 存储单元
  ┌──────────────────┐          ┌──────────────┐
  │  D 触发器        │          │   6T SRAM    │
  │  ┌──────────┐    │          │  ┌──┐ ┌──┐  │
  │  │ 20~24 个  │    │          │  │  │ │  │  │
  │  │ 晶体管    │    │          │  └──┘ └──┘  │
  │  └──────────┘    │          │   交叉耦合    │
  │  含存储+控制逻辑  │          │   锁存器     │
  └──────────────────┘          └──────────────┘
```

- **根源**：SRAM 的存储单元使用 **6 个晶体管（6T）** 组成一个交叉耦合锁存器，而 Reg（D 触发器）则需要约 **20～24 个晶体管**来实现存储+输入输出控制逻辑。
- **工程含义**：这解释了为什么容量 < 2K 时推荐使用 Reg Table，而容量 > 4K 时 SRAM 成为绝对的经济选择。

### 4.4 SRAM Bank 拆分与选 Bank 操作

当一张大 SRAM 表按深度拆分为多个 Bank 后，**每次查表都需要先选出目标 Bank**。

```
  查表地址 ├───┬───┬───┬───┐
          │B0│B1│B2│B3│      ← Bank 选择信号（高地址译码）
          └─┬─┴─┬─┴─┬─┴─┬─┘
            │   │   │   │
            ▼   ▼   ▼   ▼
         ┌─┐ ┌─┐ ┌─┐ ┌─┐
         │ │ │ │ │ │ │ │     ← 4 个 SRAM Bank
         └─┘ └─┘ └─┘ └─┘
            只有被选中的 Bank 激活
```

- 查表请求到达时，硬件根据查表地址的高位进行译码，生成 Bank 选择信号，仅激活对应的 Bank。
- **未被选中的 Bank 保持休眠状态**，不参与本次读写，从而实现动态功耗的降低。

**Bank 拆分的收益与代价：**

| 收益 | 代价 |
|------|------|
| 降低动态功耗（每次仅激活 1 个 Bank） | 总面积稍增（外围电路复制） |
| 提升工作频率（位线更短） | 漏电功耗（Leakage）增大 |
| 绕过 IP 极限 | 选 Bank 逻辑增加复杂度 |

**经验值：** "拆一半"（N=2）通常是效果不错的折中点。

### 4.5 多访问源仲裁

当 SRAM 表需要被多个访问源（例如业务流水线查表、软件 CSR 配置写表、ECC 巡检回写等）共享时，就需要引入**仲裁器**。

```
         访问源 A（业务查表）
         访问源 B（CSR 配置）
         访问源 C（ECC 回写）
                │
                ▼
        ┌───────────────┐
        │   仲裁器       │
        │  (优先级判定)  │
        └───────┬───────┘
                │
                ▼
           SRAM Table
```

- **仲裁规则**：不同访问源在同一时钟周期发起请求时，仲裁器按优先级决定哪个源获得该时钟周期的访问权。ECC 回写操作优先级通常最高，CSR 配置次之，业务查表优先级相对最低。
- **常用策略**：固定优先级（硬件开销小）或轮询 Round-Robin（公平分配）。

## 5. TCAM（三态内容寻址存储器）

### 5.1 什么是 TCAM？

这是 Table 中的"特种兵"。普通 Table 是"我给你地址，你返回数据"；TCAM 是"我给你数据，你返回地址"，并且它是**并行**的，速度快得惊人。

```
  普通存储器查找：                   TCAM 查找：
  ┌─────────────────┐              ┌──────────────────┐
  │ 输入: 地址      │              │ 输入: Key (数据) │
  │  ↓              │              │         ↓         │
  │ SRAM Array      │              │  ┌────────────┐  │
  │  → 返回该地址   │              │  │ Entry 0    │──┼─→ 匹配
  │    的数据       │              │  │[D0|M0]     │  │
  └─────────────────┘              │  ├────────────┤  │
                                   │  │ Entry 1    │──┼─→ 匹配
                                   │  │[D1|M1]     │  │
                                   │  ├────────────┤  │
                                   │  │   ...      │  │
                                   │  ├────────────┤  │
                                   │  │ Entry N-1  │──┼─→ 匹配
                                   │  │[DN-1|MN-1] │  │
                                   │  └────────────┘  │
                                   │    所有条目并行比较 │
                                   └──────────────────┘
```

它之所以叫"三态"，是因为每个比特可以存储三种状态：`0`、`1` 和 `X（Don't Care，忽略）`。

### 5.2 工作原理：Data/Mask 双阵列架构

TCAM 内部通常由两个独立的阵列组成：**Data 阵列** 和 **Mask 阵列**。

```
             TCAM 双阵列架构
      ┌────────────────────────┐
      │   Data 阵列             │
      │  ┌───┬───┬───┬───┐    │
      │  │ 1 │ 0 │ 1 │ 0 │    │
      │  ├───┼───┼───┼───┤    │
      │  │ 0 │ 1 │ 0 │ 1 │    │
      │  └───┴───┴───┴───┘    │
      │                        │
      │   Mask 阵列             │
      │  ┌───┬───┬───┬───┐    │
      │  │ 1 │ 0 │ 1 │ 1 │    │
      │  ├───┼───┼───┼───┤    │
      │  │ 0 │ 1 │ 1 │ 0 │    │
      │  └───┴───┴───┴───┘    │
      └────────────────────────┘
```

编码方式如下：

| Data | Mask | 含义 | 说明 |
|:----:|:----:|:----:|:----:|
| 0 | 0 | **X (Don't Care)** | 比较时忽略该位 |
| 0 | 1 | **0** | 必须匹配 0 |
| 1 | 0 | **1** | 必须匹配 1 |
| 1 | 1 | **Prohibited** | 禁止状态，不允许出现 |

匹配逻辑：

```verilog
Match = (Data ^ Key) & Mask;
// Mask=0 → 该位自动匹配（忽略）
// Mask=1 → 必须与 Data 相等
```

### 5.3 Valid Bit

每个 TCAM 条目还会独立存在一个 **Valid Bit**，用来标记该条目是否有效。

```
  ┌───────────────────────────────────┐
  │             TCAM 表项结构          │
  ├──────┬──────────────┬─────────────┤
  │Valid │   Data       │   Mask      │
  │ 1bit │     N bits   │   N bits    │
  ├──────┼──────────────┼─────────────┤
  │  1   │ 1010...      │ 1110...     │
  │  0   │ 0101...      │ 1011...     │  ← 此条目无效，跳过比较
  │  1   │ 1100...      │ 0111...     │
  └──────┴──────────────┴─────────────┘
```

- **Valid 位天然适合用 Reg 实现**：支持批量复位（`RST`/`FLUSH` 瞬间清零所有 Valid 位），独立引脚控制，低延迟预过滤。

### 5.4 什么时候用？

```
  需求场景 → 推荐媒介
  ┌─────────────────────────┬─────────┐
  │ 容量 < 2K，需要 1 拍出结果 │ Reg Tbl │
  ├─────────────────────────┼─────────┤
  │ 容量 > 4K，只需精确匹配   │  SRAM   │
  ├─────────────────────────┼─────────┤
  │ 需要模糊匹配 (Wildcard)   │  TCAM   │
  ├─────────────────────────┼─────────┤
  │ 多模块共享访问           │ SRAM 多口│
  └─────────────────────────┴─────────┘
```

### 5.5 多访问源仲裁

TCAM 同样存在多访问源共享同一组物理接口的情况。

```
         业务搜索请求
         CSR 配置读写
         ECC 巡检回写
         数据搬移/清空
                │
                ▼
        ┌───────────────┐
        │  TCAM 仲裁器   │
        │  (单通道串行)  │
        └───────┬───────┘
                │
                ▼
           TCAM IP
```

| 来源 | 典型优先级 | 说明 |
|------|:----------:|------|
| ECC 回写 | **最高** | 时效性高，发生概率极低 |
| CSR 配置 | **较高** | 需及时响应 |
| 业务搜索 | **较低** | 可缓冲等待 |

### 5.6 TCAM ECC 校验：外部实现

#### 为什么不在 IP 内部做？

1. **通用性**：IP 供应商保持产品通用性，不绑定特定 ECC 策略。
2. **Data/Mask 独立校验需求**：需要分别独立计算 ECC 校验位。
3. **巡检控制灵活**：外部 RTL 可灵活实现巡检 FSM。

#### 外部实现方案

```
  +─────────────────────────────────────+
  |           ECC Wrapper (外围)          |
  |  ┌─────────────┐  ┌──────────────┐  |
  |  │ ECC 编解码器 │  │ 巡检控制器 FSM│  |
  |  │ (Data + Mask) │  │              │  |
  |  └──────┬──────┘  └──────┬───────┘  |
  +─────────┼────────────────┼──────────+
            │                │
            ▼                ▼
    ┌───────┴───────┐  ┌────┴────┐
    │  TCAM IP      │  │ ECC     │
    │  Data+Mask    │  │ 校验位   │
    │  阵列          │  │ SRAM    │
    └───────────────┘  └─────────┘
```

**巡检流程：**

```
IDLE → [定时触发] → READ_DATA → CHECK_DATA → READ_MASK → CHECK_MASK → ADDR_INC → IDLE
                      ↓ (CE)            ↓ (CE)
                   [WRITE_BACK]      [WRITE_BACK]
```

- **CE（1-bit 错误）** → 硬件自动纠正并写回，上报出错地址。
- **UE（2-bit 错误）** → 触发高级别中断，等待软件介入。

---

## 6. 总结与关键设计原则

1. **目标导向**：能用 Reg 就不用 SRAM，能用 SRAM 就不用 TCAM。
2. **延迟与流水**：Reg 1-cycle，SRAM 3-cycle，TCAM 搜索 1-2 cycle。
3. **安全第一**：SRAM 必配 ECC，TCAM 避免 Data=1, Mask=1 禁止编码。
4. **初始化**：所有 Table 上电后需初始化，完成前读返回 0。
5. **地址合法性**：读写地址不能超过规格深度。

```
  │  RST ───┘                  │
  │                            │
  │  ~20-24 Transistors        │
  └────────────────────────────┘
```

### 3.2 核心特点

- **延迟低**：查表延迟固定为 **1 Cycle**，速度极快。
- **访问灵活**：可以任意读写任意比特，非常自由。
- **无校验成本**：通常情况下，Reg Table 不需要复杂的 **ECC** 逻辑来保证数据可靠性。
- **面积劣势**：与 SRAM 相比，同等容量下 Reg Table 的面积要大得多（约 **3倍**）。

### 3.3 什么时候用？——小容量表

**项目中的经验准则：**

- **硬性规则**：容量 ≤ **2K** 时，强制使用 Reg Table。
- **实际参考**：在项目中，通常容量 < **4K** 时，比较推荐使用 Reg Table。

---

## 4. SRAM Table（静态随机存取存储器）

### 4.1 什么是 SRAM？

SRAM 是一种标准的存储单元阵列，由专用的 **SRAM IP 编译器** 生成。

```
  SRAM Storage Cell (6T Structure)
  ┌──────────────────────────────┐
  │                              │
  │          VDD                 │
  │           │                  │
  │       ┌───┴───┐              │
  │       │       │              │
  │       └───┬───┘              │
  │           │                  │
  │       ┌───┴───┐              │
  │       │       │              │
  │       └───┬───┘              │
  │           │                  │
  │          GND                 │
  │                              │
  │      ~6 Transistors          │
  └──────────────────────────────┘
```

### 4.2 核心特点

- **大容量，面积优**：SRAM 是存储大容量数据最经济的硬件实现方式。
- **延迟中等**：查表延迟通常为 **3 Cycles**。
- **结构固定**：SRAM 有固定的物理结构，地址、数据、控制信号必须按照规定时序驱动。
- **需要校验**：SRAM 在先进工艺下容易受 **SEU** 影响，需要 **ECC** 保护。
- **支持写掩码**：SRAM 通常支持 **写掩码**，即可以只更新一个字中的某几个比特。

### 4.3 晶体管级面积对比：SRAM vs Reg

```
Area Ratio = 3 : 1 (Reg : SRAM, same capacity)

  Reg Cell                         SRAM Cell
  ┌──────────────────┐          ┌──────────────┐
  │ D Flip-Flop      │          │   6T SRAM    │
  │ ┌──────────┐     │          │ ┌──┐ ┌──┐   │
  │ │ 20-24    │     │          │ │  │ │  │   │
  │ │ Trans.   │     │          │ └──┘ └──┘   │
  │ └──────────┘     │          │ Cross-Coupled│
  │ Storage+Control  │          │ Latch        │
  └──────────────────┘          └──────────────┘
```

### 4.4 SRAM Bank 拆分与选 Bank 操作

```
  Address ───┬───┬───┬───┬───┐
             │B0│B1│B2│B3│      ← Bank Select (addr[high])
             └─┬─┴─┬─┴─┬─┴─┬─┘
               │   │   │   │
               ▼   ▼   ▼   ▼
            ┌─┐ ┌─┐ ┌─┐ ┌─┐
            │ │ │ │ │ │ │ │     ← 4 SRAM Banks
            └─┘ └─┘ └─┘ └─┘
              Only selected Bank activated
```

- 查表请求到达时，硬件根据查表地址的高位进行译码，生成 Bank 选择信号，仅激活对应的 Bank。
- **未被选中的 Bank 保持休眠状态**，实现动态功耗降低。

**Bank 拆分的收益与代价：**

| Advantage | Cost |
|-----------|------|
| Lower dynamic power (only 1 Bank active) | Slightly larger total area |
| Higher frequency (shorter bitlines) | Increased leakage power |
| Bypass IP limits | Added Bank-select logic |

**经验值：** "拆一半"（N=2）通常是效果不错的折中点。

### 4.5 多访问源仲裁

```
         Source A (Lookup)
         Source B (CSR Config)
         Source C (ECC Writeback)
                │
                ▼
        ┌───────────────┐
        │   Arbiter     │
        │ (Priority)    │
        └───────┬───────┘
                │
                ▼
           SRAM Table
```

## 5. TCAM（三态内容寻址存储器）

### 5.1 什么是 TCAM？

```
  Normal Memory Lookup:              TCAM Lookup:
  ┌──────────────────┐              ┌──────────────────────┐
  │ Input: Address   │              │ Input: Key (Data)    │
  │  ↓               │              │         ↓            │
  │ SRAM Array       │              │  ┌────────────┐     │
  │  → Return Data   │              │  │ Entry 0    │──┼──→ Hit/Miss
  │    at address    │              │  │[D0|M0]     │     │
  └──────────────────┘              │  ├────────────┤     │
                                    │  │ Entry 1    │──┼──→ Hit/Miss
                                    │  │[D1|M1]     │     │
                                    │  ├────────────┤     │
                                    │  │   ...      │     │
                                    │  ├────────────┤     │
                                    │  │ Entry N-1  │──┼──→ Hit/Miss
                                    │  │[DN-1|MN-1] │     │
                                    │  └────────────┘     │
                                    │ Parallel comparison │
                                    └──────────────────────┘
```

### 5.2 工作原理：Data/Mask 双阵列架构

```
         TCAM Dual-Array Architecture
      ┌────────────────────────────┐
      │   Data Array               │
      │  ┌───┬───┬───┬───┐        │
      │  │ 1 │ 0 │ 1 │ 0 │        │
      │  ├───┼───┼───┼───┤        │
      │  │ 0 │ 1 │ 0 │ 1 │        │
      │  └───┴───┴───┴───┘        │
      │                            │
      │   Mask Array               │
      │  ┌───┬───┬───┬───┐        │
      │  │ 1 │ 0 │ 1 │ 1 │        │
      │  ├───┼───┼───┼───┤        │
      │  │ 0 │ 1 │ 1 │ 0 │        │
      │  └───┴───┴───┴───┘        │
      └────────────────────────────┘
```

编码方式：

| Data | Mask | Meaning | Description |
|:----:|:----:|:--------|:-----------|
| 0 | 0 | **X (Don't Care)** | Ignore during compare |
| 0 | 1 | **0** | Must match 0 |
| 1 | 0 | **1** | Must match 1 |
| 1 | 1 | **Prohibited** | Forbidden state |

匹配逻辑：

```verilog
Match = (Data ^ Key) & Mask;
// Mask=0 → auto-match (ignore this bit)
// Mask=1 → must equal Data
```

```

```

## 6. 总结与关键设计原则

1. **目标导向**：能用 Reg 就不用 SRAM，能用 SRAM 就不用 TCAM。
2. **延迟与流水**：Reg 1-cycle，SRAM 3-cycle，TCAM 搜索 1-2 cycle。
3. **安全第一**：SRAM 必配 ECC，TCAM 避免 Data=1, Mask=1 禁止编码。
4. **初始化**：所有 Table 上电后需初始化，完成前读返回 0。
5. **地址合法性**：读写地址不能超过规格深度。

# Table 培训：问题引导式教学思路（完善版）

## 核心理念

不直接罗列知识点，而是通过**递进式问题链**，让新人带着疑问去思考每一步的设计取舍，最终自然理解 Reg、SRAM、TCAM 三种存储介质及功能组件的应用场景。

---

## 第一部分：存储类型引导（问题递进）

### Step 1：最基本的实现——Reg Table

**引导问题：**
> "芯片里有一个表，只需要存 8 条规则，每条 10 bit。你会怎么实现它？"

**解答**：用最基本的 **D 触发器（Reg）** 搭一个存储阵列即可。

**关键知识点：**
- Reg Table = D Flip-Flop 阵列，查表延迟 **1-cycle**，速度最快 [^1]
- 可以任意读写任意比特，非常灵活
- 无需 ECC 校验，可靠性自然保证 [^2]

---

### Step 2：遇到容量问题——引入 SRAM

**引导问题：**
> "现在需求变了，表需要存 100K 条规则。刚才你用的 Reg 方案，现在还好吗？"

**让新人自己思考后果：**
- Reg → 面积会大得吓人（每 bit Reg 约 20~24 个晶体管）
- 功耗也会变得不可接受
- 甚至芯片都放不下

**引入 SRAM：**
- SRAM 每 bit 只需要 6 个晶体管，同等容量面积约 Reg 的 **1/3** [^1]
- 查表延迟 **3-cycle**（包含校验和流水线开销）[^1]
- 大容量场景 SRAM 是经济选择
- 但 SRAM 需要 ECC 校验保护（先进工艺下易受 SEU 影响）[^1]

**经验规则：** 容量 ≤ 2K 硬性用 Reg，实际项目 < 4K 推荐用 Reg；> 4K 优先选 SRAM [^1]

---

### Step 3：多访问源问题——引入 SRAM 端口类型

**引导问题：**
> "现在业务流水线和软件配置都要同时访问这张表，一个表只有一个接口，怎么办？"

**方案对比：**

| 类型 | 端口数 | 典型场景 | 优缺点 |
|------|:------:|----------|--------|
| **SPRAM（单端口）** | 1R 或 1W | 单访问源表 | 面积最小，功耗最低 |
| **TPRAM（双端口）** | 1R + 1W | 业务查表+CSR配置 | 读写可同时进行，面积适中 [^3] |
| **DPRAM（双端口）** | 2R 或 2W 或 1R1W | 高并发场景 | 面积最大，灵活度最高 |

**工程要点：**
- 实际项目中绝大部分 SRAM 选用 **SPRAM**，资源最省 [^3]
- 若需多访问源，优先考虑 **TPRAM**（读、写各一路），能满足绝大多数业务+CSR 共访需求
- 若端口数 > 2，则需要引入**仲裁器**（详见第二部分功能专题）

---

### Step 4：特殊需求——内容匹配 vs. 地址匹配

**引导问题：**
> "现在我们要做一个防火墙规则表：来了一个数据包，我不关心它在第几行，我只想知道它能不能通过。也就是说：输入的是数据，想得到的是匹配结果。能直接用 SRAM 吗？"

**让新人思考 SRAM 的局限性：**
- SRAM 是"你给我地址，我返回数据"
- 这里需要的是"你给我数据，我返回是否匹配"

**引入 CAM：**
- **CAM（Content Addressable Memory）**：输入数据，并行比较所有条目，返回匹配结果
- **关键区别**：CAM 只能做**精确匹配**——数据必须完全相等才命中 [^4]

---

### Step 5：模糊匹配需求——引入 TCAM

**引导问题：**
> "现在 ACL 规则中有这么一条：'允许 192.168.1.0/24 网段的所有 IP'。注意前 24 位固定，后 8 位任意。你能用 CAM 实现吗？"

**让新人发现：**
- CAM 只能精确匹配，无法处理 X（Don't Care）状态
- 需要一种能存"通配符"的存储器

**引入 TCAM：**
- **TCAM（Ternary CAM）**：每个 bit 可存三种状态：`0`、`1`、`X（Don't Care）` [^4]
- 内部由 Data 阵列 + Mask 阵列双阵列实现
- 编码规则：`Data=0, Mask=1` → 0；`Data=1, Mask=1` → 1；`Mask=0` → Don't Care [^5]
- **Data=1, Mask=1 为禁止状态**，软件需避免写入 [^5]

---

### 第一部分总结：存储类型速查表

| 需求场景 | 推荐媒介 | 核心理由 |
|:---------|:---------|:---------|
| 小容量（< 2K），延迟敏感 | **Reg Table** | 1-cycle，无校验开销 |
| 大容量（> 4K），精确匹配 | **SRAM** | 面积最优，ECC 保护 |
| 内容匹配，无通配符 | **CAM** | 并行内容查找 |
| 内容匹配，需要通配符 | **TCAM** | 唯一支持模糊匹配的介质 |

---

## 第二部分：功能介绍（专题深入）

### 专题一：仲裁器

**引导问题：**
> "你设计的 SRAM 表只有一个物理接口，但业务查表、CSR 配置、ECC 巡检三个源都要访问它。同一时刻只能有一个源能用这个接口，怎么办？"

**解决方案：引入仲裁器**

```
         Source A (Lookup)
         Source B (CSR Config)
         Source C (ECC Writeback)
                │
                ▼
        ┌───────────────┐
        │   Arbiter     │
        │ (Priority)    │
        └───────┬───────┘
                │
                ▼
           SRAM / TCAM
```

**仲裁策略：**

| 优先级 | 访问源 | 说明 |
|:------:|:-------|:-----|
| **最高** | ECC 回写 | 纠错操作时效性高，发生概率极低，反压业务可接受 [^6] |
| **中等** | CSR 配置 | 配置响应需及时，硬件保证不被业务长期阻塞 [^7] |
| **最低** | 业务查表 | 可通过流水线缓冲等待仲裁 [^8] |

**实现方案：**
- **固定优先级**：硬件开销小，但低优先级源可能被长期阻塞
- **轮询（Round-Robin）**：公平分配带宽，但逻辑稍复杂
- **推荐**：项目中常用 **固定优先级**，ECC 回写 > CSR 配置 > 业务查表 [^6]

**设计注意事项：**
- 仲裁器引入会额外增加 **1-cycle 延迟**
- TCAM 维护接口（写条目、读条目、批量 FLUSH）是 **单通道串行** 的，仲裁器需确保同一时刻只有一路访问源使用 [^8]

---

### 专题二：Bank 拆分

**引导问题：**
> "现在有一张深 32K 的 SRAM 表，单块 SRAM IP 不支持这么深的定制。该怎么办？"

**解决方案：按深度拆分为多个 Bank**

```
  Address ───┬───┬───┬───┬───┐
             │B0│B1│B2│B3│      ← Bank Select (addr[high])
             └─┬─┴─┬─┴─┬─┴─┬─┘
               │   │   │   │
               ▼   ▼   ▼   ▼
            ┌─┐ ┌─┐ ┌─┐ ┌─┐
            │ │ │ │ │ │ │ │     ← 4 SRAM Banks
            └─┘ └─┘ └─┘ └─┘
```

**Bank 拆分的收益：**

| 收益维度 | 说明 |
|:---------|:-----|
| 绕过 IP 限制 | 突破单块 SRAM 深度/宽度上限 |
| 降低动态功耗 | 每次仅激活 1 个 Bank [^9] |
| 提升工作频率 | 更短的位线，减少寄生负载 [^9] |
| 提升访问带宽 | 不同 Bank 可并行响应互不冲突的请求 |

**Bank 拆分的代价：**

| 代价维度 | 说明 |
|:---------|:-----|
| 总面积增大 | 每个 Bank 需独立的外围电路（译码器、灵敏放大器等）[^9] |
| 漏电功耗增加 | 更多晶体管处于待机状态 |
| PR 间隙开销 | Bank 间存在物理间隙 |
| BIST 测试电路复制 | 每个 Bank 需独立测试接口 |

**工程经验：**
- **"拆一半"（N=2）** 是常见的经验折中点，收益最大，代价可控 [^9]
- Bank 不是越多越好，N > 4 时负面效应非线性加剧
- 若单 Bank 深度 < 2K，SRAM 相对 Reg 无面积优势，建议改用 Reg Table [^1]
- TCAM 的 Bank 拆分类似，但还需考虑 Valid Bit、URPF 镜像等特殊场景 [^10]

## 1. 什么是"表（Table）"？

在数字芯片中，**Table** 是核心数据结构的硬件载体，用于存储配置信息、查找规则或中间结果。

```
          Input Key (Index)
                │
                ▼
        ┌───────────────┐
        │   Table       │
        │  ┌───┬───┐   │
        │  │ 0 │ A │   │
        │  ├───┼───┤   │
        │  │ 1 │ B │   │
        │  ├───┼───┤   │
        │  │ 2 │ C │   │
        │  └───┴───┘   │
        └───────┬───────┘
                │
                ▼
      Return Data (Result)
```

**核心三要素：**
- **容量（Depth × Width）**：表能存放多少条目，以及每个条目的数据位宽。
- **访问延迟**：从发出查找请求到拿到结果需要的时钟周期数。
- **功耗与面积**：在芯片上物理实现的成本。

**培训目标：** 面对一个 Table 需求，能够快速判断应该用 Reg、SRAM 还是 TCAM 来实现。

## 2. 存储类型引导（问题递进）

### Step 1：最基本的实现——Reg Table

**引导问题：**
> "芯片里有一个表，只需要存 8 条规则，每条 10 bit。你会怎么实现它？"

**解答：** 用最基本的 **D 触发器（Flip-Flop）** 搭一个存储阵列，即 Reg Table。

```
  Reg Storage Cell (D Flip-Flop)
  ┌────────────────────────────┐
  │                            │
  │   D ────┬──── Q            │
  │         │                  │
  │  CLK ───┤                  │
  │         │                  │
  │  RST ───┘                  │
  │                            │
  │  ~20-24 Transistors        │
  └────────────────────────────┘
```

**Reg Table 特点：**

| 特性 | 说明 |
|------|------|
| **查表延迟** | **1-cycle**，速度最快 |
| **访问灵活性** | 可任意读写任意比特 |
| **ECC 校验** | 无需，可靠性自然保证 |
| **面积劣势** | 每 bit 需要 ~20-24 个晶体管 |

---

### Step 2：遇到容量问题——引入 SRAM

**引导问题：**
> "现在需求变了，表需要存 100K 条规则。刚才你用的 Reg 方案，现在还好吗？"

**让新人思考后果：**

| 问题 | 后果 |
|:----|:-----|
| **面积失控** | Reg 每 bit 约 20-24 个晶体管，100K×64bit → 近 1.5 亿晶体管 |
| **功耗爆炸** | 每个时钟周期所有 Reg 同时翻转，动态功耗不可接受 |
| **布局拥塞** | Reg 分散在逻辑区域，大量 Reg 会导致后端布局布线困难 |

**引入 SRAM：**

- SRAM 存储单元使用 **6 个晶体管（6T）** 组成交叉耦合锁存器
- 同等容量下，SRAM 面积约为 Reg 的 **1/3** [^1]

```
  SRAM Storage Cell (6T Structure)
  ┌──────────────────────────────┐
  │                              │
  │          VDD                 │
  │           │                  │
  │       ┌───┴───┐              │
  │       │       │              │
  │       └───┬───┘              │
  │           │                  │
  │       ┌───┴───┐              │
  │       │       │              │
  │       └───┬───┘              │
  │           │                  │
  │          GND                 │
  │                              │
  │      ~6 Transistors          │
  └──────────────────────────────┘
```

**SRAM 特点：**

| 特性 | 说明 |
|------|------|
| **查表延迟** | **3-cycle**（含流水线和校验开销）|
| **面积效率** | 大容量场景优势明显 |
| **ECC 校验** | 需要（先进工艺下易受 SEU 影响）|
| **写掩码** | 支持逐位更新 |

**项目中的经验规则：**

| 容量范围 | 推荐媒介 | 核心理由 |
|:---------|:---------|:---------|
| ≤ **2K** | **Reg Table** | 硬性规则，Reg 面积尚可接受 [^1] |
| < **4K** | **Reg Table** | 实际项目推荐，Reg 延迟优势更关键 [^1] |
| > **2K** | **SRAM** | 面积优势开始显现 [^1] |
| > **4K** | **SRAM** | 建议批量使用 SRAM [^1] |

### Step 3：多访问源问题——引入 SRAM 端口类型

**引导问题：**
> "现在业务流水线和软件配置都要同时访问这张表，一个表只有一个接口，怎么办？"

**SRAM 端口类型对比：**

| 类型 | 端口数 | 典型场景 | 优缺点 |
|:----|:------:|:---------|:-------|
| **SPRAM（单端口）** | 1R 或 1W | 单访问源表 | 面积最小，功耗最低 |
| **TPRAM（双端口）** | 1R + 1W | 业务查表+CSR配置 | 读写可同时进行，面积适中 [^2] |
| **DPRAM（双端口）** | 2R 或 2W 或 1R1W | 高并发场景 | 面积最大，灵活度最高 |

```
         Lookup Path                  CSR Config
             │                            │
             ▼                            ▼
      ┌──────────────┐           ┌──────────────┐
      │  Read Port   │           │  Write Port  │
      └──────┬───────┘           └──────┬───────┘
             │                          │
             └──────────┬───────────────┘
                        │
                        ▼
              ┌─────────────────┐
              │  TPRAM Instance  │
              │  (1R + 1W)      │
              └─────────────────┘
```

**工程要点：**
- 实际项目中绝大部分 SRAM 选用 **SPRAM**，资源最省 [^2]
- 若需多访问源，优先考虑 **TPRAM**（读写各一路），能满足绝大多数业务+CSR 共访需求
- 若端口数 > 2，则需要引入**仲裁器**（详见第 3.1 节）

### Step 4：特殊需求——内容匹配 vs. 地址匹配

**引导问题：**
> "现在我们要做一个防火墙规则表：来了一个数据包，我不关心它在第几行，我只想知道它能不能通过。也就是说：输入的是数据，想得到的是匹配结果。能直接用 SRAM 吗？"

**让新人思考 SRAM 的局限性：**
- SRAM 是"你给我地址，我返回数据"
- 这里需要的是"你给我数据，我返回是否匹配"

**引入 CAM：**
- **CAM（Content Addressable Memory）**：输入数据，并行比较所有条目，返回匹配结果
- **关键区别**：CAM 只能做**精确匹配**——数据必须完全相等才命中 [^3]

```
  Normal Memory:                     CAM:
  Input: Address                    Input: Key (Data)
         │                                 │
         ▼                                 ▼
  ┌──────────────┐                ┌──────────────────┐
  │  SRAM Array  │                │  Entry 0 ──► compare
  │  [0]  A      │                │  Entry 1 ──► compare
  │  [1]  B      │                │  Entry 2 ──► compare
  │  [2]  C      │                │  ...             │
  └──────┬───────┘                │  Entry N ──► compare
         │                        └────────┬─────────┘
         ▼                                 ▼
  Return Data at address          Hit / Miss + Index
```

### Step 5：模糊匹配需求——引入 TCAM

**引导问题：**
> "现在 ACL 规则中有这么一条：'允许 192.168.1.0/24 网段的所有 IP'。注意前 24 位固定，后 8 位任意。你能用 CAM 实现吗？"

**让新人发现：**
- CAM 只能精确匹配，无法处理 X（Don't Care）状态
- 需要一种能存"通配符"的存储器

**引入 TCAM：**
- **TCAM（Ternary CAM）**：每个 bit 可存三种状态：`0`、`1`、`X（Don't Care）` [^3]
- 内部由 **Data 阵列 + Mask 阵列**双阵列实现 [^4]

```
         TCAM Dual-Array Architecture
      ┌────────────────────────────┐
      │   Data Array               │
      │  ┌───┬───┬───┬───┐        │
      │  │ 1 │ 0 │ 1 │ 0 │        │
      │  ├───┼───┼───┼───┤        │
      │  │ 0 │ 1 │ 0 │ 1 │        │
      │  └───┴───┴───┴───┘        │
      │                            │
      │   Mask Array               │
      │  ┌───┬───┬───┬───┐        │
      │  │ 1 │ 0 │ 1 │ 1 │        │
      │  ├───┼───┼───┼───┤        │
      │  │ 0 │ 1 │ 1 │ 0 │        │
      │  └───┴───┴───┴───┘        │
      └────────────────────────────┘
```

**TCAM 编码规则：**

| Data | Mask | Meaning | Description |
|:----:|:----:|:--------|:------------|
| 0 | 0 | **X (Don't Care)** | 比较时忽略该位 |
| 0 | 1 | **0** | 必须匹配 0 |
| 1 | 0 | **1** | 必须匹配 1 |
| 1 | 1 | **Prohibited** | 禁止状态，不允许出现 |

**匹配逻辑：**
```verilog
Match = (Data ^ Key) & Mask;
// Mask=0 → auto-match (ignore this bit)
// Mask=1 → must equal Data
```

**Valid Bit：** 每个条目独立存在一个 Valid Bit，通过 `RST`/`FLUSH` 引脚可**批量清零**，支持条目快速清空和功耗预过滤。

```
  ┌──────────────────────────────────────┐
  │         TCAM Entry Structure         │
  ├──────┬──────────────┬───────────────┤
  │Valid │   Data       │   Mask        │
  │ 1bit │    N bits    │   N bits      │
  ├──────┼──────────────┼───────────────┤
  │  1   │ 1010...      │ 1110...       │
  │  0   │ 0101...      │ 1011...       │  ← Invalid, skip
  │  1   │ 1100...      │ 0111...       │
  └──────┴──────────────┴───────────────┘
```

**TCAM 核心特点：**

| 特性 | 说明 |
|:----|:-----|
| **并行匹配** | 1-2 cycle 即可返回所有条目的匹配结果 |
| **支持 Wildcard** | 唯一能并行完成模糊匹配的选择 |
| **面积极大** | 比 SRAM 和 Reg 都大，项目中只在关键路径使用 |
| **管理复杂** | 不支持随机写 Entry，需专门的搬移和清空逻辑 |

### Step 1-5 总结：存储类型速查表

| 需求场景 | 推荐媒介 | 核心理由 |
|:---------|:---------|:---------|
| 小容量（< 2K），延迟敏感 | **Reg Table** | 1-cycle，无校验开销 |
| 大容量（> 4K），精确匹配 | **SRAM** | 面积最优，ECC 保护 |
| 多访问源共享 | **TPRAM / 仲裁器** | 读写分离或时分复用 |
| 内容匹配，无通配符 | **CAM** | 并行内容查找 |
| 内容匹配，需要通配符 | **TCAM** | 唯一支持模糊匹配的介质 |

## 3. 功能专题

### 3.1 仲裁器：当端口数 > 2 时

**引导问题：**
> "你设计的 SRAM 表只有一个物理接口，但业务查表、CSR 配置、ECC 巡检三个源都要访问它。同一时刻只有一个源能用这个接口，怎么办？"

**引入仲裁器：**

```
         Source A (Lookup)
         Source B (CSR Config)
         Source C (ECC Writeback)
                │
                ▼
        ┌───────────────┐
        │   Arbiter     │
        │ (Priority)    │
        └───────┬───────┘
                │
                ▼
           SRAM / TCAM
```

**仲裁优先级（常用策略）：**

| 优先级 | 访问源 | 说明 |
|:------:|:-------|:-----|
| **最高** | ECC 回写 | 纠错操作时效性高，发生概率极低 [^5] |
| **中等** | CSR 配置 | 配置响应需及时 [^6] |
| **最低** | 业务查表 | 可通过流水线缓冲等待仲裁 |

**实现方案：**
- **固定优先级**：硬件开销小，但低优先级源可能被长期阻塞
- **轮询（Round-Robin）**：公平分配带宽，但逻辑稍复杂
- **工程推荐**：项目中常用 **固定优先级**，ECC 回写 > CSR 配置 > 业务查表 [^5]

**设计注意事项：**
- 仲裁器引入会额外增加 **1-cycle 延迟**
- TCAM 维护接口（写条目、读条目、批量 FLUSH）是**单通道串行**的，仲裁器需确保同一时刻只有一路访问源在使用该接口 [^7]

---

### 3.2 Bank 拆分：当单块 SRAM 规格过大时

**引导问题：**
> "现在有一张深 32K 的 SRAM 表，单块 SRAM IP 不支持这么深的定制。该怎么办？"

**解决方案：按深度拆分为多个 Bank**

```
  Address ───┬───┬───┬───┬───┐
             │B0│B1│B2│B3│      ← Bank Select (addr[high])
             └─┬─┴─┬─┴─┬─┴─┬─┘
               │   │   │   │
               ▼   ▼   ▼   ▼
            ┌─┐ ┌─┐ ┌─┐ ┌─┐
            │ │ │ │ │ │ │ │     ← 4 SRAM Banks
            └─┘ └─┘ └─┘ └─┘
              Only selected Bank activated
```

**Bank 拆分的收益：**

| 收益维度 | 说明 |
|:---------|:-----|
| 绕过 IP 限制 | 突破单块 SRAM 深度/宽度上限 |
| 降低动态功耗 | 每次仅激活 1 个 Bank [^8] |
| 提升工作频率 | 更短的位线，减少寄生负载 [^8] |
| 提升访问带宽 | 不同 Bank 可并行响应互不冲突的请求 |

**Bank 拆分的代价：**

| 代价维度 | 说明 |
|:---------|:-----|
| 总面积增大 | 每个 Bank 需独立的外围电路（译码器、灵敏放大器等）[^8] |
| 漏电功耗增加 | 更多晶体管处于待机状态 |
| 选 Bank 逻辑 | 需要地址译码器和数据选择 MUX |

**工程经验：**
- **"拆一半"（N=2）** 是常见的经验折中点，收益最大，代价可控 [^8]
- Bank 不是越多越好，N > 4 时负面效应非线性加剧
- 若单 Bank 深度 < 2K，SRAM 相对 Reg 无面积优势，建议改用 Reg Table [^1]

## 4. 安全与可靠性专题

### 4.1 SRAM ECC 校验

SRAM 在先进工艺下容易受粒子撞击导致数据翻转（**SEU**），需要 ECC 保护。

- ECC 校验逻辑在 **SRAM IP 外部** 实现，通过 Wrapper 封装 [^5]
- 校验延迟是 SRAM 查表 3-cycle 的主要原因之一 [^1]
- 1bit 错误 → 硬件自动纠正 + 回写 + 上报错误 Bank 号
- 2bit 错误 → 触发高级别中断，等待软件介入 [^5]

### 4.2 TCAM 禁止编码

**Data=1, Mask=1** 为禁止编码，软件需绝对避免写入。若误写入，可能导致：
- 内部电路工作异常（短路、过大电流风险）
- 输出不定态（X）
- 功能级错误（误匹配或漏匹配）

## 6. 项目避坑经验

1. **小表不要强行定制 SRAM**：容量 < 2K 时，SRAM 相对 Reg 无面积优势，直接用 Reg 更稳妥 [^1]
2. **SRAM 必配 ECC**：这是芯片稳定性的基本保障
3. **TCAM 编码安全**：软件需绝对避免写入 Data=1, Mask=1 的禁止编码
4. **地址合法性**：读写表地址不能超过规格深度，超限访问可能返回 X 态 [^1]
5. **初始化**：所有 Table 上电后需软件初始化，完成前读返回 0 [^1]
